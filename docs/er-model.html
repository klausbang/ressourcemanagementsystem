1. Scope

This ER model defines the current local RMS data structure, spanning resource/capability management (Phase 3-4), the technician work order and test report workflow added in Phase 7, the EUT (Unit Under Test) entity added in Phase 8, the lab/equipment mutual-exclusion constraints added in Phase 9, the standard activity template added in Phase 10, the project/discipline dashboard added in Phase 11, the staff/customer calendar added in Phase 12, the change history/audit trail added in Phase 13, plus future migration planning.

3. Diagram Notation Legend

3.1 Relationship Symbols (Crow's Foot Notation)

SymbolMeaning
||Exactly one
o|Zero or one
o{Zero or many
|{One or many

Combinations used in this diagram:

  • A ||--o{ B: one A relates to zero or many B (e.g. one customer_order has zero or many ordered_tests; one ordered_test has zero or many allocations, since a test can now have several resources assigned at once).
  • A ||--o| B: one A relates to zero or one B (e.g. one ordered_test has at most one work_order; one work_order has at most one test_report), reflecting a UNIQUE foreign key column.

Other standard crow's-foot combinations, not used here but shown for reference: A ||--|| B (one to exactly one), A }o--o{ B (many to many, both optional), A }|--|{ B (many to many, both mandatory).

3.2 Key Abbreviations

AbbreviationMeaning
PKPrimary Key — uniquely identifies each row in the table.
FKForeign Key — references the primary key of another table.
UKUnique Key — a non-primary column constrained to unique values.

4. Core Entities

  • users: login identity and role (admin/planner/technician). A technician user optionally links to one resource row (linked_resource_id) — this is how the system finds "my assigned tests" for that technician.
  • resources: procedures, equipment, facilities, technicians, and related resource records; an optional site field (Phase 9) records which lab site (e.g. TLC/TLS) an equipment/facility resource is currently at.
  • capabilities: named test capabilities; an optional discipline field (Phase 11) groups related capabilities for status reporting (e.g. CE/CI/RE/RI → "EMC").
  • resource_capabilities: many-to-many mapping between resources and capabilities.
  • customer_orders: order header per customer request; a weekly_note and waiting_for_customer flag (Phase 11) are its only manually-entered status fields — overall project status itself is derived, not stored (see Section 5).
  • milestones: a project-level date to watch for (e.g. "Draft report to customer", "EUT delivery expected") (Phase 11), shown on the dashboard.
  • staff_absences: a technician resource's vacation/absence date range with an optional reason (Phase 12), admin-managed, surfaced on the schedule (for the viewed day) and dashboard (next 14 days).
  • customer_visits: a project's customer on-site date range with optional notes (Phase 12), planner-managed, surfaced the same way.
  • activity_history: an append-only log of schedule-affecting changes to one ordered_test (Phase 13) — resource assignment/removal, reordering, EUT reassignment, and the work order lifecycle. Each row carries both a user_id FK and a denormalized username snapshot, so the log stays legible even if the user account is later renamed or removed.
  • euts: one or more Equipment/Unit Under Test records per customer order (Phase 8) — a project can involve several physical units, each tracked separately.
  • ordered_tests: one or more tests (test activities) requested under each customer order, optionally tagged to the EUT (eut_id) they belong to; an optional sequence field (Phase 10) gives its display/reorder position, scoped per (order_id, eut_id).
  • allocations: planner assignment of a resource to an ordered test; one ordered test can have several allocations (e.g. equipment, facility, and technician assigned together).
  • test_procedures: a documented test process (title, summary, prose steps, required equipment/facility, safety notes) authored against a capability; shown to technicians as reference material.
  • procedure_checks: the structured, fillable checklist for a test_procedure — one row per check-item with its pre-authored expected value.
  • work_orders: the technician's job record for one ordered_test (at most one per test) — who's doing it, which procedure, and its planned/in_progress/on_hold/completed lifecycle.
  • test_reports: the formal, fillable-and-printable test report generated from a work_order once a procedure is attached; carries the equipment-under-test identification, an overall result, and the technician-then-reviewer sign-off workflow (draft → submitted → approved/rejected).
  • report_steps: a snapshot of a test_report's checklist — each row copies one procedure_checks row's description/expected value at report-creation time, then the technician fills in the actual value and pass/fail/n-a result.
  • exclusion_groups: an admin-defined named group (e.g. "CON Chamber (TLC)") representing one shared physical constraint (Phase 9).
  • exclusion_group_resources: many-to-many mapping between exclusion_groups and facility resources — the members of a group are treated as one shared resource for conflict-checking purposes, even though each has its own resource record.
  • activity_templates: an admin-defined, named reusable sequence of standard activities (e.g. "Standard EMC Test Sequence") (Phase 10).
  • activity_template_items: the ordered activities within one activity_template (its own step_number, distinct from any ordered_tests' sequence), each with an activity name and an optional required capability; applying a template to an order/EUT copies these into new ordered_tests rows.

5. Relationship Rules

  • One customer_order has many ordered_tests, and zero or many euts.
  • One eut belongs to one customer_order, and has zero or many ordered_tests; an ordered_test's eut_id is optional (nullable), so a test activity may belong to no specific EUT (simple, single-unit orders) or to exactly one.
  • One capability can be linked to many ordered_tests as a required capability.
  • resources and capabilities are linked many-to-many through resource_capabilities.
  • Each ordered_test can have zero or many allocations, one per distinct resource, so equipment, facility, procedure, and technician resources can all be assigned to the same test; the same resource cannot be assigned twice to the same test (unique on ordered_test_id + resource_id).
  • Each allocation references one planner user to track who assigned the resource.
  • One resource can be the linked_resource_id of zero or many users (in practice exactly one technician login per technician resource, but this is an application convention, not a database constraint).
  • One capability can have many test_procedures; one test_procedure has many procedure_checks (its ordered checklist).
  • Each ordered_test has at most one work_order (unique on ordered_test_id); each work_order belongs to one technician user and, once a procedure is chosen, one test_procedure.
  • Each work_order has at most one test_report (unique on work_order_id); creating the report copies that work order's procedure_checks into new report_steps rows scoped to the report.
  • Each test_report references two distinct users: the authoring technician (technician_user_id) and, once reviewed, the approving/rejecting reviewer (reviewer_user_id) — enforced in application logic to never be the same person.
  • resources and exclusion_groups are linked many-to-many through exclusion_group_resources; a resource can belong to zero, one, or more than one exclusion group.
  • One activity_template has many activity_template_items; one capability can be linked to many activity_template_items as an optional required capability. Applying a template creates independent ordered_tests rows (with their own required_capability_id copied at that moment) — there is no ongoing link back to the template afterward, so editing a template does not retroactively change activities already created from it.
  • One customer_order has zero or many milestones, and zero or many customer_visits.
  • One resource (a technician) has zero or many staff_absences.
  • One ordered_test has zero or many activity_history entries; one user has zero or many activity_history entries as the acting user (nullable, since the recording user may be unset in edge cases).
  • A project's and a discipline's status are not stored columns — they are computed at read time from the aggregate status of the project's/discipline's ordered_tests' work_orders (app/routes_planner.py:_load_dashboard_context), per BR-001 Single Source of Truth. A discipline groups ordered_tests via their required capability's discipline field, or, for activities with no capability, a name-based fallback ("Report" if the activity name contains "report", else "Project Management").

6. Integrity Constraints

  • Unique keys on username, resource code, capability name, order code, work_order_code, and report_code.
  • Foreign keys enforce referential integrity between mapping/transactional tables and master tables.
  • Deleting an eut sets any of its ordered_tests' eut_id to NULL rather than deleting the test activities themselves (ON DELETE SET NULL) — a test activity's schedule/allocations/work order/report are not tied to the EUT record's lifetime.
  • Allocation validation in application logic ensures assigned resource has required capability for the ordered test.
  • Work order and test report status fields are constrained by CHECK to their valid lifecycle values (e.g. work_orders.status IN planned/in_progress/on_hold/completed; test_reports.status IN draft/submitted/approved/rejected); the pass/fail/n-a result columns are similarly constrained or NULL.
  • Application logic (not a database constraint) enforces the review workflow: only the report's own technician can edit or submit a draft; only a different technician or a planner can approve/reject a submitted report; rejecting requires a comment.
  • Deleting an exclusion_group cascades to its exclusion_group_resources rows (ON DELETE CASCADE); the member resources themselves are untouched.
  • Mutual-exclusion conflict checking (app/scheduling.py) is application logic, not a database constraint: starting/resuming a work order is blocked if another work order sharing a resource or exclusion group is already in_progress; a separate system-wide variant of the same check (find_all_running_conflicts) flags a project on the dashboard if any of its in-progress activities is currently in such a conflict.
  • Deleting a customer_order cascades to its milestones and customer_visits (ON DELETE CASCADE), same as its ordered_tests and euts; deleting a resource cascades to its staff_absences; deleting an ordered_test cascades to its activity_history entries.
  • activity_history is written only by application logic (app/history.py:record), never updated or deleted by the app itself — it is append-only by convention, not by a database constraint.
  • Deleting an activity_template cascades to its activity_template_items (ON DELETE CASCADE); ordered_tests previously created by applying it are untouched, since applying a template only copies values once.
  • Reordering (moving an ordered_test up/down, or an activity_template_item up/down) is a same-scope swap of two rows' sequence/step_number values in application logic, not a database constraint.

7. Migration Notes for Cloud Phase

  • Model is DB-engine agnostic and can be migrated from SQLite to PostgreSQL.
  • Preserve primary and foreign key semantics during migration.
  • Add migration scripts and indexes in deployment-readiness phase.
