1. Scope

This architecture describes the local RMS runtime — resource/capability management and order allocation (Phase 3-4), the technician work order and test report workflow added in Phase 7, the EUT (Unit Under Test) entity added in Phase 8, the lab/equipment mutual-exclusion constraints added in Phase 9, the standard activity template added in Phase 10, the project/discipline dashboard added in Phase 11, the staff/customer calendar added in Phase 12, the change history/audit trail added in Phase 13, the activity dependencies/planned dates added in Phase 14, the cross-site/planned-overlap warnings and reschedule suggestions added in Phase 15, the single-page order workspace added in Phase 16, the customer database added in Phase 17, the template application grouping added in Phase 18, the Week/Month schedule scales added in Phase 19, the admin landing page redesign/resource type restriction added in Phase 20, the further admin fixes (procedure resource type, proposal-tab preservation, resource-form retention on error) added in Phase 21, the Admin UI polish and editable-table-view prototypes added in Phase 22, the Option C prototype refinements added in Phases 23-24 alongside the UI design guide, the proposal-workflow extensions (General/New feature/Backlog, immediate save, Tester comment/Test status/Failed testing, tab-count display) added in Phases 25-26, and the Proposals Table view - the first prototype grid integrated into a real feature - added in Phase 27 — and defines how it evolves to Railway cloud deployment in later stages. See docs/srs.html section 8.13 (FR-FBK) for the proposal/feedback mechanism's full functional specification.

3. Runtime Components

  • Client layer: browser-based HTML pages, in two interfaces (Simple and Modern — see docs/dual-ui.html) for admin, planner, and technician workflows.
  • Application layer: Flask blueprints — routes_common.py (login/logout, UI-mode toggle, resource catalog, help), routes_admin.py (also manages exclusion groups since Phase 9, activity templates - now with a version counter for drift detection since Phase 18 - since Phase 10, staff absences since Phase 12, and the customer database since Phase 17; a resource's type is now a restricted choice, not free text, since Phase 20; also owns the Proposals tab's update_proposal/delete_proposal actions and, since Phase 27, bulk_update_proposals - an UPDATE-only, per-id save from the Table view that validates each row and skips rather than corrupts an invalid one), routes_proposals.py (the "P" button/dedicated-page submission flow, recording the submitter's current page/tab), routes_planner.py (also applies templates and reorders test activities since Phase 10 - grouping the activities one template application created, with delete/ungroup/sync actions, since Phase 18 - serves the project/discipline dashboard since Phase 11 - now also surfacing cross-site/planned-overlap warnings and reschedule suggestions since Phase 15, manages customer on-site visits and the schedule's absence/visit banner since Phase 12 - the schedule view also flags cross-site equipment use since Phase 15, serves the per-activity history view since Phase 13, manages activity dependencies and planned dates since Phase 14, serves the single-page order workspace since Phase 16, reusing every action above rather than duplicating them, and resolves a create/update-order submission's customer_id/new customer name since Phase 17; its schedule view also offers selectable Week/Month scales - and a combined Day+Week+Month view - alongside the original Day-only chart, since Phase 19; also serves the Visual Schedule tab and its schedule_test action since Phase 28, creating or - while still planned - updating a work order from the grid/queue), routes_technician.py (technician dashboard, work orders, blocked on an unmet dependency since Phase 14), and routes_reports.py (test report creation, fill-in, submit, and review/approval). routes_sandbox.py (Phase 22, admin-only) is a separate, deliberately unintegrated prototype area - three competing editable-table-view UIs tried against one throwaway sandbox_items table, not any real entity; Option C, the one chosen (Phase 23-24), was later (Phase 27) refactored out into a reusable client-side component so the same interaction pattern could be reused for real by the Proposals Table view without duplicating it.
  • Domain/data layer: database schema, DB connection lifecycle, schema migration helper (for in-place upgrades of an existing SQLite file - used repeatedly for the proposals table as its type/status CHECK constraints and column set grew across Phases 22-26, each time via the same rebuild-and-rename technique _migrate_users_table established), seed routines, app/scheduling.py (Phase 9: mutual-exclusion conflict checking, shared by routes_technician.py and routes_planner.py's schedule view and, since Phase 11, its dashboard; Phase 14: unmet-dependency and dependency-cycle checks; Phase 15: planned-facility-overlap and reschedule-suggestion checks; Phase 28: suggest_placement - the Visual Schedule tab's earliest-available-slot suggestion, and next_work_order_code, moved here from routes_technician.py once the planner-side Visual Schedule grid needed to create work orders the same way technician self-service already did), and app/history.py (Phase 13: append-only activity-history recording, called from both routes_planner.py and routes_technician.py at every schedule-affecting mutation).
  • Client-side shared component: app/static/js/sandbox.js exposes RmsSandbox.createEditableGrid(config) (Phase 27, extracted from the Phase 22-24 Option C prototype) - a configurable keyboard-navigable editable-grid engine (arbitrary column list, optional read-only identity column, optional add/delete-row, pluggable save callback) instantiated twice: once for the sandbox prototype (delete-all-and-reinsert save) and once for the real Admin Proposals Table view (UPDATE-only save by id). One engine, two call sites, no duplicated interaction logic.
  • Data layer (local): SQLite file database.

4. Request Flow

  1. User accesses route from browser.
  2. Flask route performs role and input validation (require_role for a single role, require_any_role where technicians and planners share access, e.g. the test reports view).
  3. Route executes queries against SQLite and applies business constraints.
  4. Route returns rendered HTML template with flash feedback. Technician and test-report pages render directly from the Modern templates regardless of the session's Simple/Modern toggle, since that workflow has no Simple-interface equivalent.

5. Security and Access (Basic)

  • Role checks enforce admin-only, planner-only, and technician-only actions, plus shared technician-or-planner access to the test reports view. The resource catalog requires any signed-in role, but is currently unlinked from navigation in both interfaces (route still functions, just hidden pending confirmed need). An anonymous visitor hitting / is served a public landing page; a signed-in user hitting /, or completing login, is routed straight to their own role's workspace (Admin, Planner, or Technician dashboard) via routes_common.py:role_home_url().
  • Session holds authenticated username and role; a technician's session is switched to the Modern UI automatically on login.
  • Input validation prevents empty required fields and invalid allocation combinations.
  • Test report edit/submit is restricted to the report's own technician; review (approve/reject) is restricted to a different technician or a planner — both enforced in routes_reports.py, not by a database constraint.

6. Environment Separation

  • Local: Flask + SQLite for fast iteration and demonstrator usage.
  • Cloud target: Railway deployment with environment variables and PostgreSQL.
  • Migration path: keep route/domain design stable; swap DB backend and add migration scripts in a later phase.
