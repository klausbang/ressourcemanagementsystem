RMS UI Design Guide

Back to Documentation Home

1. Purpose

Requested directly (proposal id 27, filed generally rather than against one page): a reference for what RMS's UI looks like, how it behaves, and how its pieces fit together - functionality, behaviour, and look and feel - so a new page in any module (Admin, Planner, Technician) reads as part of the same system rather than a one-off, and so the conventions already built up over 22 phases are written down somewhere instead of only existing as precedent scattered across templates.

This is the design-system companion to the documentation style guide (which covers how docs pages are written) and Dual Interface: Simple and Modern (which covers why two interfaces exist and exactly which pages differ between them). This guide covers the Modern interface's actual visual language in detail, since that's where almost all of the design system lives; Simple's much smaller plain-HTML vocabulary is covered in section 10.

2. Design Tokens

Every color, radius, and shadow used in the Modern interface is a CSS custom property defined once in app/static/css/modern.css's :root block, not a hardcoded value repeated per component. A new component should reuse one of these rather than introducing a new color.

4. Navigation and Wayfinding

  • Top bar (.topbar): sticky at the very top (position: sticky; top: 0), role-scoped links (only the signed-in user's own role's links render), current page highlighted via an .active class computed from request.endpoint in each template - never hardcoded per page.
  • Tabs (.tabs/.tab-list/.tab-input/.tab-panel): a CSS-only pattern with no JavaScript at all - a hidden radio per tab plus a <label for=>, and sibling-combinator CSS (#tab-x:checked ~ .tabs-body #panel-x { display: block; }) showing the matching panel. Used by Admin Manage (9 tabs) and Planner Orders (5 tabs).
    • Which tab is active on page load is decided server-side (an active_tab context variable, from a ?tab= query param), not just whichever radio happens to be marked checked in the template. Every POST action's redirect carries the right tab= value back, so submitting a form on the Resources tab returns you to the Resources tab, not tab #1 - a real bug fixed on the Planner page and later, separately, on the Admin page, because it was never carried over the first time.
    • The Admin page's tab bar is additionally position: sticky; top: var(--topbar-height) (Phase 22) so it stays visible while scrolling a long tab's content, restyled with a bordered "raised tab" look instead of a plain underline, and set to flex-wrap: nowrap; overflow-x: auto so all 9 tabs stay on one line rather than wrapping. This was deliberately scoped to Admin's own <style> block, not the shared .tab-list class in modern.css, since Planner's 5 tabs weren't asked for the same treatment.
    • Gotcha: because switching tabs is a pure CSS radio/label toggle, it never navigates - the address bar's own ?tab= only ever reflects whichever tab a real page load (or a POST redirect) last landed on, not whatever the user has since clicked over to client-side. Anything that reads "the current URL" - most notably the floating "P" proposal dialog's "reporting against" field - would otherwise silently go stale the moment someone clicks a different tab without triggering a server round trip first (Phase 25, after this broke once already). The fix has two halves: a small change listener on the tab radios calls history.replaceState() to keep ?tab= in the address bar honest with no reload, and the "P" button's click handler re-reads location.pathname + location.search at the moment it's clicked instead of trusting only the value Jinja rendered at page load. Any future pure-CSS, no-reload UI state (this app's only other candidate so far) should get the same treatment if something elsewhere needs to know "what's currently showing."
  • Quick-jump tiles (.workflow-tiles/.workflow-tile): small pill-shaped <label for="tab-x"> elements that check a tab's radio from anywhere else on the page (a label's for attribute works regardless of where in the document it sits) - used in the Admin workflow explainer so its diagram steps are directly clickable, with zero JavaScript.
  • Order-switcher / master-detail selection: query-param-driven (?overview_order_id=), same idea as tabs - state lives in the URL, not in client-side JS state, so a reload or a shared link reproduces the same view.

5. Forms and Data Entry

  • Layout: form.form-grid (a wrapping flex/grid of fields) containing one .field per input: a <label>, the control, and an optional .hint line underneath in muted small text.
  • Buttons: .btn is the base; add exactly one intent modifier - .btn-primary (the main/confirming action on a form), .btn-secondary (everything else - Save on an existing row, Cancel, navigation), .btn-danger (Delete), .btn-ghost (low-emphasis, e.g. Log out) - plus .btn-sm for compact contexts like a table row's action cell.
  • Restricted-choice fields: when a text field's real values are a small fixed set (resource type: equipment/facility/technician/procedure; proposal status; user role), use a <select>, not free text, and validate the same set server-side too (Phase 20's resource-type fix specifically closed a gap where the UI implied a fixed set but the backend still accepted anything).
  • Per-row inline edit (the single most-repeated pattern in this app - Users, Capabilities, Resources, Ordered Tests, Customers, Sandbox Option B…): each existing row's cells are real <input>/<select> elements, but they submit via a form="row-save-{id}" attribute pointing at a separate, hidden <form> placed after the closing </table> (never inside <tbody> - a <form> isn't valid there) - one such hidden form per row for Save, another for Delete. This lets every row have its own independent Save/Delete without nesting a <form> inside a <tr>.
  • Preserve typed input on a rejected save: when a create-form's validation fails (e.g. a duplicate code), re-render the page in place with the submitted values echoed back into the form, instead of falling through to a generic redirect that resets it to blank - a validation error should never look indistinguishable from "nothing happened" (Phase 21's resource-form fix, following the same precedent create_order/create_eut had already set).
  • Dirty-form tracking (Modern only, modern.js): a form's own Save button starts disabled and only enables once something in that form actually changes from its loaded state; leaving the page with any form still dirty triggers the browser's native "leave without saving?" prompt.
    • Gotcha: an auto-submitting <select onchange> (e.g. the Proposals tab's Type/Status, which save the instant you pick a value - see section 5's "auto-save on change") must call this.form.requestSubmit(), and defer it one tick with setTimeout(fn, 0) - not call this.form.submit() directly, and not call requestSubmit() synchronously inline. .submit() never fires a "submit" event at all, so dirty-tracking's cleanup never runs and the field looks permanently dirty. Calling requestSubmit() synchronously from inside the "change" handler is also wrong in a way that's easy to miss: it fires "submit" (clearing the dirty flag) before the "change" event finishes bubbling up to modern.js's own form-level "change" listener, which then immediately marks the form dirty again - right before the navigation's beforeunload check runs, producing a spurious "leave site?" prompt on every single auto-save (Phase 26, caught by an automated browser test after a direct report that it was happening). Deferring by one tick lets that bubble-phase listener finish first, so the submit-triggered clear is the last word.
  • Scroll and tab position across a save: a plain POST-redirect-GET would otherwise always land back at the top of the page. modern.js restores the scroll position (keyed by path, ignoring query string) after every such round trip, and the active tab is restored server-side as described in section 4 - together these mean clicking Save on, say, the 40th row of a long table leaves you looking at that same row afterward, not scrolled to the top of tab one.

6. Tables

  • table.modern-table wrapped in a .table-wrap div (adds a border, rounded corners, and horizontal scroll so a wide table never breaks the page layout).
  • Sortable headers: every listing table uses the macros.sort_th(label, key, table_id, endpoint) macro - a plain link (no JS) that flips <table_id>_sort/<table_id>_dir query params, server-sorted via app/table_utils.py:rows_with_meta, so several independent tables on one page (e.g. Admin's tabs) each sort independently and existing filters/tab state survive a re-sort.
  • Duplicate-row highlighting: any row whose full set of displayed columns exactly matches another row gets class .dup-row (amber background + a left accent bar) and macros.dup_flag() (a ⚠️ with an explanatory tooltip) next to its first cell - even though the underlying rows are genuinely distinct records. Also computed by rows_with_meta, keyed per-table by an explicit dup_keys list.
  • Actions column: the last column, holding that row's Save/Delete buttons (see section 5's inline-edit pattern) plus any row-specific extras (a History link, a template-group Sync button, etc.).

7. Feedback and Confirmation

  • Flash messages (.flash/.flash-info/.flash-error): rendered once, unconditionally, near the top of every page regardless of which tab is active, so an error from an action on tab 3 is never invisible because tab 1 is showing. Auto-dismiss after 6 seconds, with a manual close button too.
  • Scoped inline confirmations: for feedback that belongs visually next to the thing it's about (e.g. "Applied template 'X' (17 activities added)" shown inside the Apply-Template card itself, not just in the general flash area), use get_flashed_messages(category_filter=[...]) with a dedicated category - this can be called alongside the page's own unfiltered flash loop without consuming or duplicating the message.
  • Destructive-action confirmation: add data-confirm="Delete resource 'X'?" to the button; modern.js intercepts the click with a native window.confirm() and cancels the submit if the user declines. Every Delete button in the app uses this - never a silent, un-confirmed delete.

9. Behavioural Conventions ("state that survives a round trip")

A recurring theme across many phases: an action shouldn't disorient the user by moving them somewhere they weren't. Specifically, after any Save/Add/Delete/Apply:

  1. The scroll position stays the same (section 5).
  2. The active tab stays the same (section 4).
  3. A single-order workspace action returns to that same order's workspace, not the tabbed page or Dashboard, when it was submitted from there (a hidden return_to/return_order_id pair on the form, resolved by _redirect_after()).
  4. A proposal submitted from a specific page/tab (the floating "P" dialog) returns to that exact URL - including its query string - afterward, not just the bare page path.

When building a new action, check whether it needs the same treatment before assuming a plain redirect to the page's default view is good enough.

10. Simple UI's Plainer Vocabulary

Simple mode deliberately has almost none of the above - it renders the exact same routes and data through separate templates under templates/simple/, with no CSS framework and no JavaScript at all (see Dual Interface for the full rationale). What it does keep:

  • Plain <h2>/<h3> headings and <section> blocks instead of the page-header/card system.
  • A bare <table border="1" cellpadding="6"> instead of .modern-table - but the same macros.sort_th macro and the same .dup-row/dup-flag convention, since both are pure server-side/CSS and don't need JS.
  • The same per-row hidden-form Save/Delete pattern (section 5) - it's markup-only, so it works identically with no JS.
  • Native <details>/<summary> for the workflow explainer, same as Modern.
  • No tabs (all sections stacked on one scrollable page), no flash auto-dismiss (messages just render and stay until the next page load), no dirty-form tracking or scroll/tab restoration, no drag/keyboard-grid/spreadsheet-style features - anything requiring JS simply doesn't exist in Simple, rather than existing in a degraded form.

A handful of pages exist only in Modern at all (no Simple equivalent) because the workflow itself is JS-native or print-oriented: the Technician dashboard and Test Reports (work-order lifecycle buttons, a printable report), the Planner Schedule tab and its Day/Week/Month/All Gantt chart, and the admin-only editable-table-view sandbox. See dual-ui.html section 7 for the full list and reasoning.

11. Accessibility Basics Already in Place

  • A skip-link (.skip-link) as the very first focusable element, jumping to #main-content.
  • The tab list carries role="tablist"; each sortable column header carries aria-sort.
  • Icon-only buttons (the nav toggle, flash close button) carry aria-label; the nav toggle also reflects aria-expanded.
  • Every form field has a real <label for=>, not just a placeholder.

Not yet systematically covered: keyboard-only operation of the sandbox's custom grid (Option C) beyond its own arrow-key/Tab model, and color-contrast auditing of the badge palette. Worth a pass if this design system is extended much further.

12. Checklist for a New Page or Feature

  1. Does it belong in both UI modes, or is there a concrete reason (JS-native interaction, printability) it's Modern-only? Say so explicitly in the page and in dual-ui.html if so.
  2. Page header: eyebrow + h1 + one-sentence lead. Cards for self-contained blocks. Section-head for anything introducing a table.
  3. Any table: wrap in .table-wrap, use .modern-table, wire up sort_th and dup-row detection via rows_with_meta, give it an empty state.
  4. Any editable row: the external-hidden-form pattern (section 5), never a <form> inside <tbody>.
  5. Any new status/type: does it map onto the existing four badge colors (section 2.1) rather than inventing a new one? Is a free-text field that really has a small fixed set restricted to a <select>, validated server-side too?
  6. Any destructive action: data-confirm.
  7. Any multi-tab or multi-view page: does its own POST actions' redirects carry back whatever query param decides "which view/tab" (section 4/9), so a save doesn't bounce the user back to view #1?
  8. New icon: check section 8 before picking an emoji nothing else uses for the same concept.
  9. Update this guide, dual-ui.html, and/or phase3-backend-scope.html if the new page introduces a genuinely new pattern, not just an instance of an existing one.
