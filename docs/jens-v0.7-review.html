This is a review document for you to comment on — nothing in it has been implemented yet. Where I propose a change, I've marked it as a proposal, not a decision.

1. What these two documents are

  • JENS_SRS_EMC_Lab_v0.7.md (dated 2026-07-29, "ChatGPT + user collaboration") — a formal Danish-language SRS covering the same EMC lab scheduling problem, with its own domain model, roles, functional requirements (FR-001..039), non-functional requirements, business rules, and acceptance criteria.
  • JENS_udviklingsplan.md — a shorter development plan: MVP scope, five build phases, a recommended technical stack, a prioritized backlog, MVP acceptance criteria, and risks.

Timing note: v0.7 is dated one day before we rewrote our own SRS to v0.3 from Jens_chatgpt_historic.md (the raw chat transcript). It looks like these two files are the same customer/consultant conversation's own polished output, rather than a separate, later round of discovery. That matters for how to read this review: it's largely a completeness check against what we already mined from the transcript, not a wholly new requirements set — but a few items either weren't in the transcript we saw, or were given a different priority here than we assumed. Worth confirming with the customer whether v0.7/the udviklingsplan supersede the transcript, or sit alongside it.

2. Verdict summary

Most of v0.7 is already covered by RMS as built (Phases 3–13) — often at a level of detail v0.7 doesn't even ask for (multi-resource allocation, change history, a project dashboard, a staff/customer calendar). No area was a total surprise.

Two things deserve real attention:

  1. Activity dependencies (v0.7 FR-021–024, all Must) don't exist in RMS at all today — we only have a cosmetic display sequence, not an enforced "B can't start before A finishes" rule. Both v0.7 and the udviklingsplan treat this, and the rescheduling it enables, as central. Our own SRS currently files most of this under Phase 14 as a stretch goal (Could/Should) — v0.7 disagrees and marks it Must. See Section 4.
  2. The udviklingsplan's recommended tech stack (React/Next.js, FastAPI or Node, PostgreSQL, JWT/SSO, Docker+CI/CD) is a generic greenfield recommendation that assumes nothing has been built yet. It doesn't match what RMS already is (Flask + Jinja2 server-rendered dual-UI, SQLite locally, Railway/Postgres planned later). This needs an explicit decision from you — see Section 3.

My read: this looks like a stock recommendation for starting a project from zero, not a response to what actually exists after 13 delivered phases. Rewriting the frontend in React/Next.js and the backend in FastAPI/Node would mean re-building everything already working, for reasons the udviklingsplan doesn't state (it never argues the current stack is inadequate — it just wasn't aware of it). Two clean options, not a forced choice:

  • Continue incrementally on Flask/Jinja2, moving SQLite → PostgreSQL and adding real auth (password/SSO) when it's time to leave localhost — this was already the plan and keeps all delivered work.
  • Treat the udviklingsplan's stack as a deliberate future rewrite (e.g. once the requirements/UX are fully proven out on Flask, a React frontend could be built against the same data model without re-deriving the requirements) — a much bigger, separate decision.

Proposal: keep Flask/SQLite→PostgreSQL for now unless you tell me the customer specifically wants the React/FastAPI stack; I won't start a rewrite without that being an explicit instruction.

4. Gap analysis: what v0.7 asks for vs. what RMS does today

v0.7 areav0.7 saysRMS todayProposal
Dependencies
FR-021..024, Must		 An activity can depend on another; scheduling is blocked until the prerequisite is met; parallel-vs-not is configurable; a hard rule that "report" can't start before its test ends. No dependency concept exists. ordered_tests.sequence is a cosmetic reorder position (Phase 10), not an enforced blocker — a planner can start a "Report" work order before its test is complete today. New phase: "Activity dependencies." Add an optional depends_on_ordered_test_id (or a small dependency join table if one activity should depend on more than one), block start_work_order/resume_work_order with a clear message when the prerequisite isn't completed (mirrors the existing Phase 9 conflict-block pattern), and auto-link the "obvious" case — a Report activity depending on its own EUT's non-Report activities — when a template is applied.
Planned schedule (dates/duration)
FR-004, FR-006, Must		 Each activity carries an expected start date, expected end date, and duration, entered at planning time — independent of whether it has actually started. ordered_tests has no date fields at all. work_orders.scheduled_date is a single date (no end/duration), and started_at/completed_at only populate once a technician actually acts. There is no way today to see "this is planned for Aug 10–12" before work begins. Add optional planned_start_date/planned_end_date (or a duration) to ordered_tests or work_orders, planner-editable independent of actual execution. This also unlocks a real "delayed" status (comparing planned vs. actual), which v0.7's status list has and ours doesn't (see next row).
"Delayed" status
implied by FR-005, FR-029		 A project/activity status list explicitly includes delayed, alongside pending/ongoing/completed/waiting. RMS computes Planned/In Progress/Reporting/Completed/Waiting-for-Customer, but nothing corresponds to "delayed" — there's no planned-date baseline to be late against (see row above). Once planned dates exist, add a derived "Delayed" flag (planned end date in the past, not completed) rather than a manually-set status — keeps BR-001 Single Source of Truth intact.
Enforce staff availability
FR-013, Must		 The system shall prevent scheduling a person during a recorded absence, not just show it. Phase 12 only displays a technician's absence as a banner on the schedule/dashboard; nothing stops a work order from being started/assigned during it. Extend the existing Phase 9 conflict-block (find_running_conflict) to also check the assigned technician's staff_absences on the work order's scheduled/actual date, reusing the same block-and-explain pattern.
Staff overload view
FR-014, Should		 Show when a technician is over-booked. No utilization/overload view exists. A small addition to the Dashboard: count of concurrently-scheduled work orders per technician per day; flag >1 as an overload warning. Lower priority than the two above.
Week view
FR-008, Must		 Switch between day, week, and project views. The schedule/Gantt view is day-only, navigated one day at a time. (Already an open question in our own SRS since Phase 12, now reinforced here.) Add a week-at-a-glance strip (7 mini day-columns or a condensed week grid) alongside the existing day Gantt, rather than replacing it — the day view stays the detailed one.
Unstaffed activities
Section 7.1 business rule		 An activity can be run with no technician assigned (e.g. an unattended climate-chamber soak). work_orders.technician_user_id is NOT NULL — every work order must have a technician today. Relax to nullable, with the technician dashboard/"my tests" filter treating unassigned work orders as visible to all technicians (or a planner-only "unattended" flag) rather than owned by one person.
Excel import
FR-038, Should		 Import existing projects/plans from Excel. Not implemented (our SRS doesn't schedule it either). Worth reconsidering only if it would materially ease the customer's transition off Sprint.xls/Projects.xls — a one-time migration script rather than an ongoing feature might be enough; recommend confirming actual need before building it.
Drag-and-drop / bulk edit
udviklingsplan risk mitigation		 Named directly as a risk mitigation: "prioritize drag-and-drop and bulk editing" to reduce manual update burden. All edits are one row/one form at a time; no drag-and-drop scheduling. Lower priority UX improvement; worth a design conversation once dependencies/planned-dates exist, since drag-and-drop rescheduling is much more useful once the system knows what else would need to move.
Export (CSV/Excel/PDF)
FR-032, Could		 Export planning data. Not implemented. Both documents agree this is low priority (Could). No change proposed unless a concrete need surfaces — matches our existing FR-INT-1 stance.

8. Suggested next step

Pending your comments above, my recommendation is a new phase focused narrowly on activity dependencies and planned dates (Section 4, rows 1–2), since almost every other gap and escalation in this review (delayed status, "show consequences of a change", the eventual Phase 14 rescheduling assistant, even drag-and-drop) either depends on it or becomes far more useful once it exists. Everything else in this document can follow independently, in whatever order you'd prioritize after reviewing.
