Getting started

A quick guide to the two interfaces, the two roles, and how the main workflows fit together.

🖥️ Simple vs. Modern

This app has two interfaces showing exactly the same data: Simple (plain HTML, no styling) and Modern (this one — styled, tabbed, card-based). Switch anytime with the Switch to Simple / Switch to Modern button in the top bar. Your choice is remembered for your session.

👤 Roles

Log in with just a username — this is a local demonstrator with no passwords.

  • RMS Administrator (admin.demo): manages users, capabilities, resources, and which capabilities each resource has.
  • Test Planner (planner.demo): manages customer orders, the tests ordered under them, and which resources are assigned to each test.
  • Test Technician (technician.demo, technician2.demo): sees the tests assigned to them, creates and runs work orders against a test procedure, fills in the test report, and reviews reports submitted by other technicians.

🔧 Admin workflow

  1. Create capabilities (e.g. "Vibration Test") on the Capabilities tab.
  2. Create resources — equipment, facilities, procedures, technicians — on the Resources tab.
  3. On the Capability assignments tab, link each resource to the capabilities it has, so planners can find it for matching tests.
  4. Manage user accounts and roles on the Users tab.
  5. If two facility resources are really the same shared physical chamber (e.g. two setups in one room), put them in the same exclusion group on the Exclusion groups tab — the schedule will then flag two activities in that group if their times overlap, and starting one while the other is running is blocked.
  6. Maintain reusable activity templates (e.g. "Standard EMC Test Sequence") on the Activity templates tab — an ordered list of standard activities, each optionally requiring a capability, that a planner can apply to an order/EUT to bulk-create its test activities in one step.
  7. Record a technician's vacation/absence dates on the Staff absences tab — the planner's Schedule tab and dashboard will flag it automatically.

🗂️ Planner workflow

  1. Create a customer order (order code, customer name, product name) on the Customer orders tab.
  2. If the order involves more than one physical unit, add each as an EUT (Equipment/Unit Under Test) on the Customer orders tab — this is optional and can be left out for a simple, single-unit order.
  3. Add one or more ordered tests to that order on the Ordered tests tab, each optionally requiring a capability and optionally tagged to the EUT it belongs to — or, on the same tab, apply an activity template (e.g. "Standard EMC Test Sequence") to bulk-create a whole standard sequence in one step, then use the ▲/▼ buttons to reorder, or add/remove activities per project as needed.
  4. On the Resource assignment tab, assign resources to each test. A test can have several resources at once — e.g. equipment, a facility, and a technician together. Only resources with the test's required capability are offered, and the same resource can't be assigned twice to one test.
  5. Check the Dashboard for an overview of every active project: its status and per-discipline status (generated from the underlying activities, not typed in separately), any live resource conflicts, activities still missing a work order or a test procedure, upcoming milestones, and customer on-site visits. The weekly note, "waiting for customer" flag, and customer visits are the only things you set by hand there.
  6. Record a customer on-site visit against a project directly on the Dashboard — it shows up there and, for the day itself, as a banner on the Schedule tab alongside any technician absence.

🧰 Technician workflow

  1. The Technician dashboard shows every ordered test where the technician's linked resource has been assigned by a planner.
  2. For each test, open Create work order, optionally pick a matching test procedure, set a scheduled date, and add notes.
  3. Move the work order through its lifecycle: Start (planned → in progress), Hold/Resume if interrupted, then Complete with a pass/fail/n-a result and closing notes.
  4. The selected test procedure's steps, required equipment, facility, and safety notes are shown alongside the work order so the technician has everything needed to perform the test.
  5. A read-only Test procedure library tab lists every documented test process for reference.

An admin links a technician's user account to a technician resource on the Admin → Users tab (field "Linked technician resource") — that's what determines which assigned tests appear for them.

📄 Test reports

  1. Once a work order has a test procedure assigned, the technician can Create test report — this generates a fillable template pre-loaded with the equipment/facility used, the technician's name, the unit-under-test's name (from the order), and one row per procedure check-item with its expected value.
  2. The technician fills in the equipment serial number, the actual value and pass/fail/n-a result for each step, an overall result, and any notes, then Submits for review — this locks the report and time-stamps the technician's sign-off.
  3. Any other technician or a planner can then open it from Test Reports → Awaiting your review and Approve or Reject it (a comment is required on rejection). A rejected report can be reopened by its technician for corrections and resubmitted.
  4. The report page doubles as a printable A4 form — use the Print / Save as PDF button at any stage (blank template during the test, or the completed and signed report afterwards).

📊 Table features

  • Sorting — click any column header to sort by it; click again to reverse direction.
  • Duplicate highlighting — a row shaded amber (with a ⚠️ next to its first cell) has the exact same values in every displayed column as another row in that table. It's a hint to check for an accidental duplicate entry, not an error on its own.

🔗 Referential integrity

Deletes are blocked with a clear message if they would leave other data dangling — e.g. you can't delete a capability that's still required by an ordered test, or a resource/user still referenced by an allocation. Deleting a customer order or an ordered test, however, intentionally cascades and removes its dependent tests/allocations, since those only make sense in context.
