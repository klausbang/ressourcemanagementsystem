Route Scope

  • GET / : public landing page (guides an anonymous visitor to log in); redirects a signed-in user straight to their own role's workspace (Admin/Planner/Technician), not the catalog
  • GET /catalog : resource catalog with filters (requires a signed-in admin, planner, or technician); implemented but currently unlinked from navigation in both interfaces, reachable only by direct URL
  • Admin scope (single POST-dispatch route, action field per operation): full CRUD on users, capabilities, and resources (including a resource's optional site); assign/remove capability-to-resource mapping; link a technician user to their resource; full CRUD on exclusion groups and their facility-resource membership (Phase 9); full CRUD on activity templates and their items, including reordering an item up/down within its template (Phase 10)
  • Planner scope (single POST-dispatch route, action field per operation): full CRUD on customer orders, EUTs (Phase 8), and ordered tests (optionally tagged to an EUT); assign multiple resources to an ordered test (one allocation per resource) and remove any one of them independently; a day-view Schedule/Gantt tab (Modern UI) that flags any two visible activities sharing a resource or exclusion group whose actual/inferred time windows overlap (Phase 9); apply an activity template to an order/EUT, bulk-creating its ordered tests in the template's order, and reorder any existing ordered test up/down within its order/EUT scope (Phase 10)
  • GET/POST /planner/dashboard (Phase 11, planner role): lists active projects with a derived status (see below), per-discipline status breakdown, unscheduled/missing-procedure counts, a live-conflict flag, and milestones, plus a read-only completed-projects table; actions to save a project's weekly note/waiting-for-customer flag, and to create/delete a milestone
  • Technician scope (routes_technician.py, single POST-dispatch route): dashboard of tests allocated to the technician's linked resource; create a work order per assigned test; set/change its test procedure; move it through planned/in_progress/on_hold/completed (start/resume are conflict-checked, see below); edit notes
  • Test report scope (routes_reports.py): create a report from a work order (snapshots that procedure's check-items); fill in and save a draft report; submit for review; approve/reject a submitted report (any technician other than the author, or a planner); reopen a rejected report; list reports pending the current user's review and full report history
  • Basic login/logout for role-aware actions; login switches a technician's session to the Modern UI automatically

Validation Rules (Minimum)

  • Required fields on create/update forms
  • Unique username, resource code, capability name, order code, work_order_code, and report_code (checked on both create and update, excluding the row being edited)
  • Role field restricted to admin/planner/technician on user create/update
  • Order must exist before adding an EUT or an ordered test to it; an ordered test's EUT, if selected, must belong to the same order (Phase 8)
  • Allocation requires resource to have the test's required capability, and the same resource cannot be assigned twice to the same ordered test (unique on ordered_test_id + resource_id) — a test can otherwise have any number of different resources allocated at once (e.g. equipment, facility, procedure, and technician together)
  • A work order requires a test procedure to be set before a test report can be generated from it; at most one work order per ordered test and at most one test report per work order (both enforced by a UNIQUE column)
  • A test report can only be submitted once every step has a result and an overall result is set; only the report's own technician may edit or submit it; only a different technician or a planner may approve/reject it, and rejecting requires a comment
  • Deletes that would violate a foreign key (e.g. deleting a capability still required by an ordered test, a resource or user still referenced by an allocation) are caught and reported with a specific reason instead of a raw database error
  • Deleting a customer order cascades to its ordered tests, all of their allocations, work orders, test reports, and report steps, and its EUTs; deleting an ordered test cascades the same way at that level. These cascades are enforced at the database level (ON DELETE CASCADE), not in application code. Deleting an EUT does not cascade to its ordered tests — it clears their eut_id back to NULL instead (ON DELETE SET NULL), since a test activity's schedule/allocations/results are not tied to the EUT record's lifetime
  • Role checks for admin/planner/technician actions; the resource catalog itself requires any signed-in role (it is no longer visible to anonymous visitors)
  • (Phase 9) Starting or resuming a work order is blocked, with a message naming the conflicting work order/activity, if another work order sharing a resource or exclusion group is already in_progress (app/scheduling.py:find_running_conflict) — not a database constraint, since it depends on live status across multiple ordered tests
  • (Phase 10) Applying a template requires the target order to exist and, if an EUT is given, that it belongs to that order; each created ordered test's sequence continues on from the highest existing value in that order/EUT scope. Moving an ordered test or a template item up/down is a same-scope swap of two rows' sequence/step_number values, with no effect at either end of the list. Deleting a template item renumbers the remaining items 1..N so gaps don't accumulate; deleting a template cascades to its items but never touches ordered_tests already created from it
  • (Phase 11) A project's and a discipline's status are computed, not stored, from the aggregate status of the project's/discipline's ordered_tests' work_orders (app/routes_planner.py:_load_dashboard_context): Completed once every activity's work order is completed; In Progress once any activity is or has been worked; Reporting once every non-Report activity is completed but at least one Report-discipline activity isn't; otherwise Planned. The waiting_for_customer flag, when set, overrides the displayed status to "Waiting for Customer" regardless of the computed value

Table Sorting and Duplicate-Row Highlighting

  • Every listing table (resource catalog; admin users, capabilities, resources, resource-capability mapping, exclusion groups, and activity templates; planner customer orders, EUTs, ordered tests, and resource assignment) has clickable, sortable column headers for every displayed column.
  • Sorting is implemented server-side with no JavaScript: each header is a link that sets a table-scoped <table_id>_sort / <table_id>_dir query parameter (e.g. resources_sort=code&resources_dir=desc), so multiple independent tables on one page (e.g. the four admin tables) sort independently, and existing filters are preserved when re-sorting.
  • Any row whose full set of displayed columns exactly matches another row in the same table is flagged and highlighted (amber background, .dup-row), even though the underlying database row is distinct (different primary key). This surfaces cases such as two identical ordered tests added to the same order.
  • Sorting and duplicate detection share one helper, app/table_utils.py:rows_with_meta, applied per table in each route.
