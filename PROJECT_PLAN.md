# RMS Development Plan (Local to Cloud)

Last updated: 2026-08-02
Plan source: /memories/session/plan.md

## Goal
Build a lean first version of the Resource Management System by moving through three stages: static mockups, working local app, then Railway deployment. Keep documentation-first delivery in HTML, include architecture and ER diagrams as embedded PNG/SVG, and introduce basic role checks in the first working local version.

## Steps
1. Phase 1 - Scope Baseline and Documentation Skeleton
2. Extract the minimum SRS scope from the prompt into concise requirement groups: business context, user roles, core workflows, and non-functional constraints. This is the baseline for all later deliverables.
3. Define the documentation structure and navigation for a landing page that links SRS, architecture, ER model, development plan, and AI questions page.
4. Create a single documentation style/layout guideline so all pages share consistent headings, section order, and cross-links.
5. Phase 2 - First Demonstrator (Static Mockup, Local)
6. Specify static HTML wireframes (no backend dependency) for the essential workflows: resource catalog view, resource capability assignment view (admin), and resource-to-order assignment view (planner).
7. Prepare dummy example data aligned with the prompt scenarios (multimeter calibration order, vibration/humidity tests for a mobile phone product).
8. Define acceptance checks for mockups: visible role-specific pages, clear navigation, and representational data for resources/capabilities/orders.
9. Phase 3 - Minimal Working Local Application
10. Design backend scope for Flask + SQLite local runtime: entities, routes, validation rules, and minimal template rendering needed to support the two core role actions.
11. Add basic role checks in this stage (admin vs planner) with lightweight authentication/authorization suitable for demonstrator use.
12. Implement local CRUD and assignment flows in dependency order: resource/capability management first, then order/resource allocation.
13. Add seed script or seed routine for demo data so documentation scenarios are reproducible.
14. Phase 4 - Architecture and Data Design Deliverables
15. Produce web application architecture document describing client, Flask app layer, service/domain logic, data access, and SQLite database; include environment separation notes for future Railway deployment.
16. Produce ER model document covering core entities and relationships: users/roles, resources, capabilities, resource-capability mapping, customer orders, ordered tests, and resource allocations.
17. Embed architecture and ER diagrams as PNG/SVG in HTML documentation and cross-link them from the landing page.
18. Phase 5 - Cloud Deployment Readiness and Final Stage
19. Define deployment activities for Railway as a later stage: configuration variables, production database target (PostgreSQL), migration strategy from SQLite model, and deployment verification checklist.
20. Add staged rollout path in the plan: static local mockup -> working local Flask+SQLite -> stable packaged app -> Railway deployment.
21. Include post-deployment operational tasks: smoke tests, role-flow checks, and documentation updates.
22. Phase 6 - AI Collaboration and Open Questions Governance
23. Create an AI questions page in HTML with priority tags: Blocker, High, Medium, Low.
24. Seed initial unresolved questions around business rules and allocation constraints (for example, scheduling conflicts, capacity limits, and order priority rules).
25. Define a triage process for answering and retiring questions as requirements mature.
26. Phase 7 - Technician Workflow and Test Reports
27. Add a Test Technician role: a technician user account optionally links to its own technician resource, which determines which planner-allocated tests appear on that user's dashboard.
28. Build a technician dashboard (Modern UI only) showing assigned tests, the equipment/facility allocated alongside the technician, and a per-test work order lifecycle (planned/in_progress/on_hold/completed).
29. Add a test procedure library (capability-scoped process description, required equipment/facility, safety notes) plus a structured, ordered checklist of check-items with pre-authored expected values, for use in test reports.
30. Add test report generation from a work order: a fillable template pre-loaded with test/order/equipment identification, technician name, unit-under-test fields, and one row per check-item with its expected value; technician fills in actual values, results, overall result, and notes.
31. Add a technician-then-reviewer sign-off workflow (draft -> submitted -> approved/rejected, reopenable on rejection), where the reviewer must be a different technician or a planner, plus a shared reports queue/history view.
32. Style the test report as a single printable A4 page usable both blank (during the test) and completed (after sign-off).
33. Refresh core documentation (SRS, architecture, ER model/diagram, dual-UI notes, backend scope) to describe the Phase 7 additions, and produce a one-page sales brochure summarizing RMS capabilities.
34. Phase 8 - EUT (Unit Under Test) as a First-Class Entity
35. Add an EUTs table so a project can hold multiple EUTs, each with a name and optional serial number.
36. Let a test activity (ordered_test) optionally reference the EUT it belongs to, without breaking existing EUT-less test activities.
37. Extend planner UI (Simple and Modern) to manage EUTs per order and tag test activities to one.
38. Seed a multi-EUT demo order and update ER model/diagram and architecture docs to describe the EUT entity.
39. Phase 9 - Lab and Equipment Mutual-Exclusion Constraints
40. Model mutual-exclusion groups of facility resources (e.g. CON chamber: CE/CI; SAC chamber: RE/RI) that cannot run with overlapping time windows.
41. Enforce the conflict check when a planner schedules or reschedules a work order, with a clear explanation of which activity it conflicts with.
42. Add a site field (TLC/TLS) to facility/equipment resources and warn (not block) on cross-site overlap of shared equipment.
43. Surface constraint conflicts inline in the existing schedule/Gantt view.
44. Phase 10 - Standard Project Activity Template
45. Define a reusable, ordered standard activity template (Kick-off through EUT return) that an admin/planner can maintain.
46. Let a planner apply the template to a new EUT to bulk-create its test activities in one step, then freely reorder/add/remove per project.
47. Phase 11 - Project and Discipline Dashboard
48. Add project-level status and a weekly free-text note, replacing the equivalent Sprint.xls columns.
49. Derive discipline-level status from underlying test activity/work order status rather than separate manual entry.
50. Build a dashboard listing active projects with status, discipline status, and upcoming milestones, plus a read-only completed-projects history view.
51. Surface constraint conflicts and activities missing an EUT/date/procedure on the dashboard.
52. Phase 12 - Staff and Customer Calendar
53. Add staff absence/vacation records per technician and customer on-site day records per project.
54. Surface both on the schedule and dashboard views for the affected dates.
55. Phase 13 - Change History and Audit Trail
56. Add an append-only history record for schedule-affecting changes to a test activity (resource assignment, scheduling, status).
57. Add a per-activity history view answering "who moved this, when, and why."
58. Phase 14 - Activity Dependencies and Planned Dates
59. Let a planner declare that a test activity depends on one or more other activities within the same project, and block starting/resuming its work order until every prerequisite is completed.
60. Let a planner record an optional planned start/end date on a test activity, independent of its actual execution, and surface an "overdue" flag on the dashboard when a planned end date has passed without completion.
61. Phase 15 - Dynamic Rescheduling Assistant (stretch, Could)
62. Let a facility reservation span multiple consecutive days as a single booking.
63. When an activity is delayed, failed, or its EUT is replaced, suggest how directly dependent downstream activities (now using Phase 14's real dependency data, rather than just template ordering) could shift, for the planner to accept or ignore manually. Full automatic optimization/conflict auto-resolution stays out of scope.
64. Phase 16 - Single-Page Customer Order Workspace
65. Build a one-page view for creating a customer order and maintaining everything directly attached to it (EUTs, test activities with their dependencies/planned dates/resource allocations, milestones, customer visits, and derived status), reusing the tabbed Planner page's and Dashboard's existing actions rather than duplicating them.
66. Wire an order-switcher and entry points (nav link, per-order "Workspace" link, activity history back-link) so the page is reachable both fresh (create a new order) and for maintaining any existing one.
67. Phase 17 - Customer Database
68. Add a customer database (name plus optional contact/address fields) that a planner can pick from when creating or editing an order, without preventing the order from being placed if the customer isn't already in it or isn't fully filled out.
69. Let a new customer be entered inline during order creation/edit; if its required contact information isn't all provided, surface it as an outstanding item for the admin to complete later rather than blocking the planner.
70. Phase 18 - Template Application Grouping
71. Group the test activities created by one "Apply Template" action together wherever activities are listed, tagging each with the template it came from, with the ability to delete the whole group, or remove/ungroup one activity from it, at once.
72. Detect when the template itself has changed since a group was applied and offer a one-click sync that adds any new template activities the group is missing, without touching activities the planner has already customized.
73. Phase 19 - Week/Month Schedule Scales
74. Let the planner switch the production schedule chart between Day (existing hourly view), Week, and Month scales, with a selectable number of weeks (default 1) or months (default 1) shown.
75. Let the planner see Day, Week, and Month stacked together at once (Day on top, Week below it, Month at the bottom) as an alternative to switching between them one at a time.
76. Phase 20 - Admin Landing Page Redesign and Resource Type Restriction
77. Redesign the Admin landing page: keep the workflow explainer and the functional tab menu, collapse the entity-count strip behind a small expand control by default, make the workflow explainer's steps clickable (jumping to the matching tab), and show each tab's entity count (with a highlighted attention count) beneath its label.
78. Preserve the Admin page's selected tab across a Save/Add/Delete round trip, matching the Planner page's existing behavior.
79. Make the floating proposal-report dialog draggable by its title bar.
80. Restrict a resource's type to the fixed set already in use (equipment, facility, technician) instead of free text, enforced server-side.
81. Phase 21 - Further Admin Fixes
82. Add "procedure" as a fourth allowed resource type.
83. Preserve the active tab when submitting a proposal, instead of always returning to the Users tab.
84. Preserve the admin's typed values in the create-resource form when the save is rejected (e.g. a duplicate code), instead of silently clearing it.
85. Phase 22 - Admin UI Polish and Editable-Table-View Prototypes
86. Collapse the Admin page's "How this page fits in your workflow" explainer by default.
87. Make the Admin page's tab header row sticky (fixed just below the site header) and restyle it to look more like a classic tabbed interface, compact enough to fit all 9 tabs on one line.
88. Make submitted proposals fully editable by the admin (title, description, type, in addition to the existing status/comment), and show each proposal's numeric ID for cross-referencing.
89. Build three different working prototypes of an editable, paste-from-Excel/CSV/JSON table view, in an admin-only sandbox area, backed by real sample data and sample CSV/JSON/Excel files, for review before deciding whether to integrate one into the real Admin/Planner tables.
90. Phase 23 - Editable-Grid Refinements (Option C)
91. Following review of the three sandbox prototypes, refine the chosen one (Option C, the custom keyboard-navigable grid): a more visible selection highlight; standard Ctrl+C/Ctrl+V/Ctrl+X keyboard shortcuts; undo (icon and Ctrl+Z); a row-selector column for whole-row copy/delete; clickable column headers for whole-column selection; and a top-left corner cell for select-all.
92. Phase 24 - Search/Filter, Multi-Row Edit, and a UI Design Guide
93. Add a search/filter toggle to the Option C grid: a magnifying-glass icon reveals a per-column filter row, supporting wildcards (<code>*</code>, <code>?</code>) and <code>|</code> for OR.
94. Add a "select rows, edit the first, repeat to the rest" bulk-edit tool to the Option C grid: a pencil icon plus Ctrl+R.
95. Write a UI design guide covering the app's visual language, components, and behavioural conventions, for consistency across roles and modules and to explain the UI to a new reader.
96. Phase 25 - Proposal System Enhancements
97. Add a "General - not related to this view only" checkbox, a "New feature" proposal type, and a "Backlog" status to the proposal submission form and the Admin Proposals tab.
98. Fix the proposal-submission "reporting against" path/tab tracking, which had regressed to no longer recording which tab was active on the Admin page.
99. Save a proposal's Type and Status changes immediately when changed in the Admin Proposals tab, without waiting for the Save button.
100. Phase 26 - Sandbox Row Counts, Proposal Workflow Fields, and Fixes
101. Show total/visible/selected row counts in the sandbox Option C grid.
102. Fix a spurious "leave without saving?" prompt triggered every time Type or Status auto-saves in the Admin Proposals tab.
103. Add a "Tester comment" field, a "Test status" dropdown (Waiting/Passed/Failed/Passed with comments), and a "Failed testing" status option to the Proposals tab.
104. Show the Proposals tab's count as total, accepted-and-waiting-for-implementation (green), and new-needing-review (red), e.g. "31 (2) (1!)".
105. Phase 27 - Proposals Table View
106. Add a "Form view"/"Table view" toggle to the Admin Proposals tab; Table view is an editable grid with the same functionality as the sandbox Option C prototype (keyboard nav, rectangular/row/column selection, Ctrl+C/X/V, undo, wildcard/OR filter, multi-row edit via Ctrl+R), operating on the real proposal rows.
107. Phase 28 - Visual Scheduling (Phase 1 of a multi-phase proposal)
108. Add a "Visual Schedule" tab to the Planner page: a queue of unscheduled ordered tests (earliest-needed first), placeable onto a technician x day grid by click, keyboard, or drag-and-drop.
109. Compute a suggested placement (earliest technician with the matching capability, free that day, not on staff leave, no same-day conflict on any equipment/facility already allocated to the test) per queued test, one-click-acceptable or manually overridable.
110. Modern-only for the grid/drag/keyboard interaction; give Simple UI the same underlying placement action through a plain per-row technician-select + date-input form so no UI mode loses data access.
111. Phase 29 - Drag-to-Reschedule on the Visual Schedule Grid
112. Make an already-placed, still-`planned` test's grid chip itself selectable and draggable, so it can be moved to a different technician/day the same way an unscheduled queue item is placed - reusing the same schedule_test action rather than a new one.

## Verification
1. Documentation completeness check: landing page links to all required pages and each page links back to landing.
2. SRS scope check: includes only minimal requirements needed for first demonstrator and explicitly marks out-of-scope items.
3. Mockup review check: static pages cover both required role workflows and both sample customer order scenarios.
4. Local app functional check: admin can add resources/capabilities and assign capabilities; planner can assign resources to orders.
5. Role check validation: unauthorized role cannot execute the other role's protected action.
6. Data design check: ER model relationships support many-to-many mapping where needed (resource-capability and order-resource allocation).
7. Deployment readiness check: Railway deployment checklist exists and maps local configuration to production equivalents.
8. EUT check: a project can have multiple EUTs; test activities can optionally be tagged to one and filtered/reported per EUT.
9. Constraint check: two activities in the same mutual-exclusion group cannot be scheduled with overlapping windows; the rejection names the conflicting activity and time.
10. Template check: applying the standard activity template creates all its activities, in the chosen order, in one step.
11. Dashboard check: project/discipline status and milestones are derived from underlying activity data, not entered a second time, and stay consistent with it.
12. Calendar check: a technician's absence and a customer's on-site day are visibly flagged on the schedule/dashboard for the correct dates.
13. History check: a schedule-affecting change to a test activity produces a visible history entry recording who changed it and when.
14. Dependency check: an activity with an unmet prerequisite cannot be started or resumed, the rejection names the prerequisite, and it becomes startable once every prerequisite is completed; a self-dependency or circular chain is rejected when created.
15. Planned-date check: an activity's planned end date in the past without a completed work order is flagged as overdue on the dashboard, without changing its own computed status.
16. Cross-site check: two activities visible on the Schedule tab the same day, sharing an equipment resource, whose facilities are at different sites, are flagged (not blocked) unless already a hard resource conflict.
17. Planned-overlap check: two activities sharing a facility/exclusion group with overlapping planned date ranges are flagged on the dashboard even before either has a work order.
18. Reschedule-suggestion check: a late prerequisite with a dependent activity that has its own planned dates produces a suggestion naming the delay and the proposed new dates; accepting shifts the dates and logs history, ignoring leaves them unchanged; neither the same pair nor its dates are re-suggested afterward.
19. Order workspace check: creating an order from the workspace's own form lands directly on that order's workspace page, and every action performed from the workspace (EUT/activity/dependency/resource/milestone/visit/weekly-note changes) lands back on the same workspace rather than a tab or the Dashboard, while the same actions performed from the classic tabbed page or Dashboard are unaffected.
20. Order workspace consistency check: status, conflict, overdue, and planned-clash flags shown on the workspace exactly match what the Dashboard shows for the same order, since both read from the same underlying computation.
21. Customer database check: creating/editing an order offers existing customers for selection plus a free-text new-customer fallback; an order can be placed with a brand-new, incomplete customer with no blocking validation, and that customer appears on the admin's Customers tab flagged as needing more information until its contact name, email, and address are all filled in.
22. Template grouping check: activities created by one "Apply Template" action are shown together, tagged with the template name; deleting the group removes all its member activities in one action, while removing/ungrouping one activity leaves the rest of the group and the activity itself intact; editing a template after a group was applied from it marks the group as out of date, and syncing adds only the activities the group is missing without altering or removing any activity already in it.
23. Schedule-scale check: switching the schedule chart between Day/Week/Month/All shows the expected column granularity (hourly for Day, daily for Week/Month) and the expected number of columns for the selected week/month count; all three scales stay anchored to the same viewed date when switching, and a work order's bar appears in the correct place and is clipped correctly at the edges of every scale.
24. Admin tab-persistence check: submitting any admin action (create/update/delete on any tab) redirects back to the tab it was submitted from, not always the Users tab.
25. Resource-type check: the Resources tab's type field only offers equipment/facility/technician, and a direct POST with any other value is rejected server-side with a clear message.
26. Proposal-tab check: submitting a proposal from a specific Admin tab returns to that same tab, not the Users tab.
27. Resource-form-retention check: submitting a duplicate resource code re-renders the create-resource form with every typed field (code, name, type, status, site) still filled in, plus a clear error message, rather than a blank form.
28. Admin tab-bar check: the tab header row stays visible (sticky) while scrolling the Admin page, and all 9 tabs fit on one line without wrapping.
29. Proposal-editing check: an admin can change a proposal's title, description, and type (not just status/comment), and every proposal shows its numeric ID.
30. Sandbox check: each of the three prototype pages can insert a row one-by-one, paste/import a batch of rows (from a same-shape paste, a CSV file, and a JSON file), and export/copy the table back out, without ever touching real Admin/Planner data.
31. Option C refinement check: a row handle selects/copies/deletes a whole row; a column header selects a whole column; the corner cell selects everything; Ctrl+C/Ctrl+X/Ctrl+V and Ctrl+Z all work as expected; the selection highlight is visibly darker than before.
32. Filter check: a wildcard/OR filter pattern (e.g. <code>INV-* | EQP-*</code>) correctly narrows the visible rows in the Option C grid without changing what gets saved/exported; closing the filter restores every row.
33. Multi-row-edit check: selecting 2+ rows, editing the first, and pressing Ctrl+R repeats that row's values onto every other selected row in one step, undoable in one Ctrl+Z; selecting fewer than 2 rows is rejected with a clear message; Esc cancels without applying anything.
34. Proposal-system check: a proposal can be marked General, filed as a New feature, and set to Backlog status; changing Type or Status in the Admin Proposals tab saves immediately, no Save click needed.
35. Tab-tracking check: clicking between Admin tabs (a pure CSS toggle, no page reload) keeps the address bar's <code>?tab=</code> in sync, so submitting a proposal from any tab - reached by a server round trip or just a client-side tab click - records and returns to that same tab.
36. Sandbox row-count check: the Option C grid's status line always shows the correct total/visible/selected row counts, updating live as rows are added/removed/filtered/selected.
37. Auto-save-no-warning check: changing Type or Status in the Admin Proposals tab saves immediately and never triggers the browser's "leave without saving?" prompt.
38. Proposal test-workflow check: a Tester comment, Test status, and "Failed testing" proposal status all save and display correctly; the Proposals tab count shows total/accepted(green)/new(red!) in the format "N (A) (M!)".
39. Proposals Table view check: switching the Admin Proposals tab to Table view shows the same proposals as an editable grid with the same Option C interactions (selection, copy/paste, undo, filter, multi-row edit); the ID column is read-only; there's no add/delete-row in this view; editing a cell and clicking Save persists by id without disturbing fields the grid doesn't expose (description, path, submitted_by_username, created_at); an invalid Type/Status/Test-status value typed into a cell is skipped on save rather than corrupting the row.
40. Visual Schedule check: an unscheduled ordered test can be placed by clicking a grid cell, by keyboard (Tab to the cell's button, Enter/Space), or by dragging its queue card onto a cell; each path creates a work order with the chosen technician/date and removes the test from the queue. Re-placing a still-`planned` work order updates it in place (no duplicate row); a work order that has moved past `planned` can no longer be moved from this tab. A technician lacking the test's required capability is still allowed with a warning flash, not blocked. The suggested slot shown per queued test changes (or disappears) once the suggested technician is marked absent that day. Simple UI offers the same placement action via a plain technician-select + date-input form with no grid/drag/JS involved.
41. Drag-to-reschedule check: an already-placed, still-`planned` test's grid chip can be dragged, clicked, or keyboard-selected then placed on a different cell, updating the same work order (no duplicate row) rather than creating a new one; a chip for a test past `planned` renders as a plain, non-interactive label instead of a link, and is neither selectable nor draggable. A "currently selected" banner distinguishes an unscheduled-queue selection from an already-placed one, with a Cancel-selection link.

## Decisions
- Local database for first working versions: SQLite.
- First stage UI: static HTML wireframes only.
- Role handling: include basic role checks in first working local version.
- Diagram embedding format in docs: PNG/SVG.
- Cloud deployment timing: final stage after stable local app.
- Duration estimates excluded by request; plan is activity/task based.
- Customer discovery source for Phases 8-14: a shared ChatGPT conversation transcript with the customer, archived to the repo as `Jens_chatgpt_historic.md` for traceability.
- SRS restructured as v0.3 around the chapter list the customer's own consultant proposed (Projects, Test Plan, Resources, Constraints, Calendar, Status Management, Planning, Rescheduling, Visualization, Reporting, Integrations, Usability, Nice-to-have), with Must/Should/Could priority and a BR/FR/AC numbering split, per explicit customer request. Existing v0.1/v0.2 requirements were carried forward unchanged in meaning and marked Delivered.
- A test activity's EUT reference (Phase 8) is optional, not mandatory, so existing single-EUT projects and previously-created test activities keep working without a data migration forcing a value onto them.
- Phases 8-14 are deliberately kept small and independently demoable, so customer feedback after each one can confirm (or redirect) the approach before the next phase is committed.
