Route Scope

  • GET / : public landing page (guides an anonymous visitor to log in); redirects a signed-in user straight to their own role's workspace (Admin/Planner/Technician), not the catalog
  • GET /catalog : resource catalog with filters (requires a signed-in admin, planner, or technician); implemented but currently unlinked from navigation in both interfaces, reachable only by direct URL
  • Admin scope (single POST-dispatch route, action field per operation): full CRUD on users, capabilities, and resources (including a resource's optional site); assign/remove capability-to-resource mapping; link a technician user to their resource; full CRUD on exclusion groups and their facility-resource membership (Phase 9); full CRUD on activity templates and their items, including reordering an item up/down within its template (Phase 10); create/delete staff absences (Phase 12)
  • Planner scope (single POST-dispatch route, action field per operation): full CRUD on customer orders, EUTs (Phase 8), and ordered tests (optionally tagged to an EUT, and, since Phase 14, an optional planned start/end date); assign multiple resources to an ordered test (one allocation per resource) and remove any one of them independently; a Schedule/Gantt tab (Modern UI) with a Day scale that flags any two visible activities sharing a resource or exclusion group whose actual/inferred time windows overlap (Phase 9), also flags non-overlapping same-day use of shared equipment at two different sites (Phase 15), and shows a banner for any technician absent or customer on-site on the viewed day (Phase 12), plus Week and Month scales and a combined "All" view (Phase 19); apply an activity template to an order/EUT, bulk-creating its ordered tests in the template's order, and reorder any existing ordered test up/down within its order/EUT scope (Phase 10); an "Orders overview" tab offering List/Kanban/Master-detail presentations of the same order data; add/remove a same-project activity dependency (Phase 14)
  • GET /planner/activity/<ordered_test_id>/history (Phase 13, planner role): one activity's full change history, newest first; links back to the activity's order workspace (Phase 16)
  • GET /planner/order/new and GET /planner/order/<order_id> (Phase 16, planner role): a single-page workspace to create a customer order and then maintain everything attached to it - EUTs, test activities (with dependencies, planned dates, and resource allocations), milestones, customer visits, and derived status - on one page instead of the tabbed Planner page's five tabs. Reuses every existing action from the routes below with no new logic of its own: every form on the workspace carries hidden return_to=order/return_order_id fields so the same actions redirect back to the workspace instead of the tabbed page or Dashboard
  • create_order/update_order (Phase 17): accept either an existing customer_id (from a picker) or a new_customer_name/plain customer_name field, resolving to a customers row either way - matched by name if one already exists, else created fresh with just that name
  • exclude_from_template_group, delete_template_group, sync_template_group (Phase 18, planner role): remove one activity from its template application group (keeping the activity itself), delete a whole group and its member activities together, or add whatever template activities are missing since the group was applied/last synced
  • Admin scope also gains: create_customer/update_customer/delete_customer (Phase 17) - full CRUD on the customer list, blocked on delete while any order still references that customer, and a rename propagates to the denormalized customer_name on every order pointing at it
  • (Phase 20) Every admin action's POST redirect now carries a tab query param (via an ACTION_TAB lookup keyed by action name) so the page reopens on the tab the action belongs to, instead of always resetting to the Users tab - the same fix already applied to the Planner page's tabs; create_resource/update_resource now also reject a resource_type outside the fixed equipment/facility/technician set, matching the picker the UI now offers instead of a free-text field
  • GET/POST /planner/dashboard (Phase 11, planner role): lists active projects with a derived status (see below), per-discipline status breakdown, unscheduled/missing-procedure counts, a live-conflict flag, milestones, and customer on-site visits (Phase 12), an overdue-activity flag (Phase 14), a planned-facility-overlap flag and a dashboard-wide list of reschedule suggestions (Phase 15), plus a read-only completed-projects table and a dashboard-wide staff-availability list (absences in the next 14 days, Phase 12); actions to save a project's weekly note/waiting-for-customer flag, to create/delete a milestone or a customer visit, and to accept or ignore a reschedule suggestion (Phase 15)
  • Technician scope (routes_technician.py, single POST-dispatch route): dashboard of tests allocated to the technician's linked resource; create a work order per assigned test; set/change its test procedure; move it through planned/in_progress/on_hold/completed (start/resume are conflict-checked, see below); edit notes
  • Test report scope (routes_reports.py): create a report from a work order (snapshots that procedure's check-items); fill in and save a draft report; submit for review; approve/reject a submitted report (any technician other than the author, or a planner); reopen a rejected report; list reports pending the current user's review and full report history
  • Basic login/logout for role-aware actions; login switches a technician's session to the Modern UI automatically

Validation Rules (Minimum)

  • Required fields on create/update forms
  • Unique username, resource code, capability name, order code, work_order_code, and report_code (checked on both create and update, excluding the row being edited)
  • Role field restricted to admin/planner/technician on user create/update
  • Order must exist before adding an EUT or an ordered test to it; an ordered test's EUT, if selected, must belong to the same order (Phase 8)
  • Allocation requires resource to have the test's required capability, and the same resource cannot be assigned twice to the same ordered test (unique on ordered_test_id + resource_id) — a test can otherwise have any number of different resources allocated at once (e.g. equipment, facility, procedure, and technician together)
  • A work order requires a test procedure to be set before a test report can be generated from it; at most one work order per ordered test and at most one test report per work order (both enforced by a UNIQUE column)
  • A test report can only be submitted once every step has a result and an overall result is set; only the report's own technician may edit or submit it; only a different technician or a planner may approve/reject it, and rejecting requires a comment
  • Deletes that would violate a foreign key (e.g. deleting a capability still required by an ordered test, a resource or user still referenced by an allocation) are caught and reported with a specific reason instead of a raw database error
  • Deleting a customer order cascades to its ordered tests, all of their allocations, work orders, test reports, and report steps, and its EUTs; deleting an ordered test cascades the same way at that level. These cascades are enforced at the database level (ON DELETE CASCADE), not in application code. Deleting an EUT does not cascade to its ordered tests — it clears their eut_id back to NULL instead (ON DELETE SET NULL), since a test activity's schedule/allocations/results are not tied to the EUT record's lifetime
  • Role checks for admin/planner/technician actions; the resource catalog itself requires any signed-in role (it is no longer visible to anonymous visitors)
  • (Phase 9) Starting or resuming a work order is blocked, with a message naming the conflicting work order/activity, if another work order sharing a resource or exclusion group is already in_progress (app/scheduling.py:find_running_conflict) — not a database constraint, since it depends on live status across multiple ordered tests
  • (Phase 10) Applying a template requires the target order to exist and, if an EUT is given, that it belongs to that order; each created ordered test's sequence continues on from the highest existing value in that order/EUT scope. Moving an ordered test or a template item up/down is a same-scope swap of two rows' sequence/step_number values, with no effect at either end of the list. Deleting a template item renumbers the remaining items 1..N so gaps don't accumulate; deleting a template cascades to its items but never touches ordered_tests already created from it
  • (Phase 11) A project's and a discipline's status are computed, not stored, from the aggregate status of the project's/discipline's ordered_tests' work_orders (app/routes_planner.py:_load_dashboard_context): Completed once every activity's work order is completed; In Progress once any activity is or has been worked; Reporting once every non-Report activity is completed but at least one Report-discipline activity isn't; otherwise Planned. The waiting_for_customer flag, when set, overrides the displayed status to "Waiting for Customer" regardless of the computed value
  • (Phase 12) A staff absence's end_date cannot be before its start_date, same for a customer visit; both are checked at the day level (inclusive start/end) against the schedule's viewed day and, for absences, a rolling 14-day-ahead window on the dashboard
  • (Phase 13) Every schedule-affecting mutation (resource assign/remove, reorder, EUT change, work order create/start/hold/resume/complete, procedure change) writes one activity_history row via app/history.py:record in the same transaction as the change itself, with a system-generated detail string; reason is only populated where the acting form already collects a note (currently: work order completion notes). History rows are never updated or deleted by the application
  • (Phase 14) An activity dependency must be within the same order, cannot reference itself, and is rejected if it would create a circular chain (app/scheduling.py:would_create_dependency_cycle, a graph walk over existing prerequisites) — not a database constraint, since it depends on the shape of the whole dependency graph, not just the one row being inserted. Starting or resuming a work order is blocked, naming the outstanding prerequisite, if any of its activity's prerequisites doesn't have a completed work order yet (app/scheduling.py:find_unmet_dependency), checked after the Phase 9 resource-conflict check. A planned end date in the past with no completed work order is surfaced as a derived "overdue" flag on the dashboard, not stored as its own status
  • (Phase 15) Two visible Schedule-tab activities that share an equipment resource whose facilities put them at different sites are flagged (not blocked) unless that pair is already flagged as a hard resource conflict (app/routes_planner.py:_load_schedule_context, activity_site derived from the first facility-type allocation with a site set). Two activities sharing a facility/exclusion group with overlapping planned date ranges are flagged on the dashboard even with no work order yet (app/scheduling.py:find_planned_facility_overlaps). A reschedule suggestion is computed (not stored) whenever a prerequisite finished late or is overdue and its dependent has its own planned dates set (app/scheduling.py:find_reschedule_suggestions); accepting one updates the dependent's planned dates and, like ignoring, records a reschedule_dismissals row so the same (dependent, prerequisite) pair is not suggested again
  • (Phase 16) The order workspace introduces no new validation of its own - every action it submits to (app/routes_planner.py:_redirect_after) is exactly the one the tabbed Planner page or Dashboard already uses, so the same rules above apply unchanged; the only difference is where the browser lands afterward (the workspace instead of a tab), decided by a hidden return_to/return_order_id pair on each form rather than a second code path per action
  • (Phase 17) A customer name is unique; picking an existing customer always takes precedence over a typed new name if both are somehow present. Deleting a customer is blocked, with a specific reason, while any order still references it - there is no cascade, unlike most other master-data deletes in this app, since silently detaching a real customer relationship from historical orders would lose information rather than just tidy it up
  • (Phase 18) A template's version (not a timestamp) is bumped on every item add/edit/delete/reorder (app/routes_admin.py:_touch_template), and compared against a group's stored applied_template_version to flag it stale - deliberately not a last-modified timestamp, since two changes within the same minute-resolution timestamp used elsewhere in this app would otherwise be indistinguishable. Syncing a stale group only adds template activities not already present in it, matched by name; it never removes or overwrites an existing group member, so a planner's customizations to it are never silently lost. Deleting a template application group deletes its member activities at the application level (and everything that already cascades from an ordered_test's own deletion - allocations, dependencies, history) rather than via a declared foreign key, for the same ADD-COLUMN-safety reason as ordered_tests.template_application_id and customer_orders.customer_id below
  • (Phase 19) The Week/Month schedule scales place bars with the exact same clip/offset rules as the Day chart (app/routes_planner.py:_place_bars, a shared helper parameterized by slot size - 1 hour for Day, 24 hours for Week/Month), just at a coarser granularity, so there is only one bar-placement algorithm to keep correct rather than three. sched_weeks/sched_months query params are clamped server-side to [1, 8] and [1, 6] respectively regardless of what a crafted URL requests, silently falling back to the default (1) on a non-integer value rather than erroring. Week always starts on the Monday of the viewed date's week and Month always starts on the 1st of the viewed date's month, so switching scales never jumps to an unrelated range - all three scales stay anchored to the same viewed date. The Day chart's live conflict/cross-site overlay is deliberately not recomputed for Week/Month (see SRS FR-PLN-5 design note); the underlying hard block at work-order start/resume (Phase 9) is unaffected by which scale is being viewed, since that check has nothing to do with the Gantt display.
  • (Phase 20) A resource's resource_type must be one of equipment/facility/technician (app/routes_admin.py:RESOURCE_TYPES) on both create and update - enforced server-side, not only by the <select> the UI now offers, so a direct POST can't bypass it. A customer/proposal's "needs admin attention" count shown per-tab on the Admin page (see SRS FR-USE-7) is derived at read time from the same is_complete/status == 'new' facts already computed for the Customers/Proposals tabs, not a second stored flag
  • (Phase 21) RESOURCE_TYPES extended with procedure as a fourth allowed value - it isn't treated specially anywhere else in the codebase (unlike facility/equipment, which the Phase 9/15 conflict/cross-site checks key off of), so this was a one-line constant change plus its usual server-side validation. On a create_resource validation failure (missing fields, invalid type, or a duplicate code), the route now re-renders the Admin page in place with the submitted values retained (resource_form_values) and the Resources tab forced active, instead of falling through to the shared end-of-action redirect that reset the create-resource form to blank

Table Sorting and Duplicate-Row Highlighting

  • Every listing table (resource catalog; admin users, capabilities, resources, resource-capability mapping, exclusion groups, activity templates, and staff absences; planner customer orders, EUTs, ordered tests, and resource assignment) has clickable, sortable column headers for every displayed column.
  • Sorting is implemented server-side with no JavaScript: each header is a link that sets a table-scoped <table_id>_sort / <table_id>_dir query parameter (e.g. resources_sort=code&resources_dir=desc), so multiple independent tables on one page (e.g. the four admin tables) sort independently, and existing filters are preserved when re-sorting.
  • Any row whose full set of displayed columns exactly matches another row in the same table is flagged and highlighted (amber background, .dup-row), even though the underlying database row is distinct (different primary key). This surfaces cases such as two identical ordered tests added to the same order.
  • Sorting and duplicate detection share one helper, app/table_utils.py:rows_with_meta, applied per table in each route.
