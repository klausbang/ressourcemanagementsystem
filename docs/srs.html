Resource Management System (RMS) - SRS v17

Version: 0.17 | Date: 2026-08-06

1. Purpose

This SRS defines the requirements for RMS, a web-based planning and execution system for a test laboratory. It replaces three separate spreadsheets/documents the customer currently maintains by hand for every project — a project-pipeline sheet ("Sprint.xls"), a production/resource schedule ("Projects.xls"), and a per-EUT test plan — with one system built around a single source of truth.

2. Vision and Guiding Principles

  • Single Source of Truth. A test activity's status, schedule, and result exist in exactly one place. Every other view (test plan listing, production schedule, dashboard) is generated from that one record, not a manually-copied restatement of it. This directly targets the customer's stated problem: the same fact (e.g. "CE passed") today has to be re-entered in up to four places (testplan, Projects.xls, Sprint.xls, and sometimes twice in Projects.xls).
  • Activity-centric planning, not project-centric. The system plans and schedules test activities (an EUT going through RE, ESD, a report being written, etc.), not projects as monolithic blocks. A project is a container for its EUTs, and each EUT is a container for its activities. This is what lets a single delay, failure, or hardware swap be absorbed by moving a handful of activities instead of rebuilding a spreadsheet.
  • Design note (challenging this model): some workflows may be better served by treating the project as the primary planning unit (e.g. very small orders with a single EUT and no cross-activity dependencies). RMS keeps the project and EUT as real entities precisely so this can be revisited per project type without a data model change — see Section 13.

3. Glossary

TermMeaning
ProjectA customer's test engagement. Modeled by the existing customer_orders entity (order_code, customer_name).
EUTEquipment/Unit Under Test — one physical item being tested under a project. One project can have several EUTs (e.g. two prototype phones with different serial numbers).
Test ActivityA single planned/executed task against an EUT: a standard test (RE, CE, ESD, ...), report writing, review, or logistics (EUT delivery/return). Modeled by the existing ordered_tests entity.
ResourceAnything that can be allocated to an activity: test equipment, a lab/facility, a technician, or a documented procedure.
Lab / ChamberA facility-type Resource with physical capacity for one activity at a time (e.g. the CON chamber used for CE/CI, the SAC chamber used for RE/RI).
DisciplineA grouping used for status reporting (e.g. EMC, Radio, Safety, Report) — distinct from an individual test activity.
SiteOne of the customer's two physical labs (TLC, TLS); some equipment is shared and moves between them.

4. Business Context

  • The company performs electrical, mechanical, and environmental tests on customer products across two lab sites (TLC and TLS).
  • Today the same information is tracked and manually re-entered across a project-pipeline sheet, a production schedule sheet, and a per-EUT test plan, which the customer has identified as fragile: a single schedule change (a test overrunning, a failure, new hardware from the customer, an absent engineer) requires editing many fields by hand across documents.
  • Example orders include multimeter calibration and vibration/humidity tests for a mobile phone under development.

5. User Roles

  • RMS Administrator: manages resources, capabilities, assignments of capabilities to resources, user accounts, and a technician user's link to their own technician resource.
  • Test Planner: manages projects and EUTs, plans and schedules test activities, and assigns resources to them.
  • Test Technician: works the tests assigned to them — runs a work order against a documented test procedure, fills in and submits the resulting test report, and reviews/approves or rejects reports submitted by other technicians.

No new role was identified in customer discovery beyond these three; the dashboard, calendar, and history views planned below are read/edit surfaces for the Test Planner (and, for their own tests, the Test Technician), not new roles.

6. Domain Model

Project (customer_orders)
 |-- EUT (euts)                       [Planned - Phase 8]
 |     `-- Test Activity (ordered_tests)
 |           |-- Resources (allocations -> resources)
 |           |-- Work Order + Result (work_orders)
 |           |-- Test Report (test_reports -> report_steps)
 |           `-- History (audit trail)  [Planned - Phase 13]
 |-- Milestones                       [Planned - Phase 11]
 `-- Status / Notes                   [Planned - Phase 11]

Design principle: every view (test plan, schedule, dashboard) is generated by querying this one model; nothing is denormalized into a second copy that must be kept in sync by hand.

7. Requirement Notation

  • BR-nnn (Business Requirement): why the system needs to do something, in the customer's terms.
  • FR-<area>-n (Functional Requirement): what the system shall do, grouped by area code (PRJ, TP, RES, CON, CAL, STA, PLN, RSC, VIS, RPT, INT, USE, FBK, NTH — one per subsection of Section 8). Area-coded rather than one flat sequence, so a later phase can add FR-CON-4 without renumbering unrelated requirements.
  • AC-<FR id>.n (Acceptance Criterion): how a specific functional requirement is verified. Applied to the requirements most likely to be contested by a reviewer or supplier, not exhaustively to every line.
  • Priority: Must (blocks the phase), Should (expected, can slip one phase), Could (nice-to-have, not scheduled).
  • Status: Delivered (implemented, phase noted) or Planned (phase noted; see PROJECT_PLAN.md for the phase's task breakdown).

8. Functional Requirements

8.1 Projects (FR-PRJ)

BR-001: The laboratory needs one place to create and track a customer engagement instead of a row in Sprint.xls.

  • FR-PRJ-1 [Must, Delivered - Phase 3]: The system shall allow planners full CRUD on customer orders (order code, customer name, product name).
  • FR-PRJ-2 [Must, Delivered - Phase 8]: A project shall be able to hold one or more EUTs (see 8.2), each with its own test activities.
  • FR-PRJ-3 [Should, Delivered - Phase 11]: A project shall carry an overall status (Planned, In Progress, Reporting, Completed, or Waiting for Customer) and a free-text weekly note, replacing the equivalent Sprint.xls columns. Of these, only the weekly note and the "waiting for customer" flag are stored/manual — the status itself is derived (see FR-STA-2), since a second manually-typed copy of already-known information is exactly the duplication BR-001 exists to remove.
  • FR-PRJ-4 [Could, Delivered - Phase 11]: Completed projects shall remain visible in a read-only project history view.
  • BR-007 [added Phase 17, from a planner-submitted proposal]: Retyping a customer's name on every new order risks the same name drifting into several slightly different spellings over time, with no single place to hold that customer's contact details.
  • FR-PRJ-5 [Should, Delivered - Phase 17]: The system shall let a planner pick an existing customer from a known-customer list when creating or editing a customer order, or type a new customer's name inline without it needing to already exist in that list.
  • FR-PRJ-6 [Should, Delivered - Phase 17]: A customer record created this way (name only) shall be flagged to the administrator as needing further contact information, without ever blocking the order itself from being placed or saved.

8.2 Test Plan and EUTs (FR-TP)

BR-002: The laboratory needs to plan and track tests per physical unit under test, not only per project, since a project can involve several EUTs on independent schedules.

BR-006 [added Phase 14, from customer SRS v0.7 review]: An activity that requires another to finish first (the clearest customer example: a report can't be written before its test is complete) must be an enforced rule, not merely a suggested display order — the existing sequence field (Phase 10) only controls display/reorder position and does not block an out-of-order start.

  • FR-TP-1 [Must, Planned - Phase 8]: The system shall let a planner record one or more EUTs per project, each with a name/description and an optional serial number.
  • FR-TP-2 [Must, Planned - Phase 8]: The system shall let a test activity optionally reference the EUT it belongs to, so activities can be filtered and reported per EUT as well as per project. Existing activities created before this requirement, or created without selecting an EUT, remain valid (the reference is optional, not mandatory), preserving current behavior for simple single-EUT projects.
  • FR-TP-3 [Must, Delivered - Phase 3]: The system shall allow planners full CRUD on test activities within a project, each with a name and a required capability.
  • FR-TP-4 [Should, Delivered - Phase 10]: The system shall offer a reusable, ordered standard activity template (e.g. Kick-off, Testplan, EUT delivery, RE, RI, CI, CE, Burst, Surge, Voltage Dips, Power Frequency Magnetic Field, other tests, ESD, Report writing, Report review, Report to customer, EUT return) that a planner can apply to an order/EUT to bulk-create its activities in one step, then freely reorder, add to, or remove from per project.
  • FR-TP-5 [Must, Delivered - Phase 14]: The system shall let a planner declare that a test activity depends on one or more other activities within the same project, and shall block starting or resuming its work order until every one of those prerequisites is completed.
  • FR-TP-6 [Should, Delivered - Phase 14]: The system shall let a planner record an optional planned start and end date on a test activity, independent of its actual execution timestamps, so a plan can exist before any work begins.
  • FR-TP-7 [Could, Delivered - Phase 18]: The activities created by one "apply template" action (FR-TP-4) shall be grouped together, so the planner can delete or exclude individual members from the group as a unit; the group shall be flagged if the source template has since changed, offering to add whatever new template activities aren't already present.
  • AC-FR-TP-1.1: Given a project with 0 EUTs, when a planner adds an EUT and adds a test activity under it, then the activity is visible both on that EUT's test plan and, unfiltered, on the project's full activity list, without being entered twice.
  • AC-FR-TP-4.1: Given an EUT with no test activities, when a planner applies the "Standard EMC Test Sequence" template to it, then all of the template's activities are created in one step, in the template's order, each carrying over its template-defined required capability (if any); the planner can then move any one activity up or down within that EUT independently of the template.
  • AC-FR-TP-5.1: Given "Report writing" depends on "CE", when a technician attempts to start or resume the Report writing work order while CE's work order is not completed, then the system rejects the action and names which prerequisite activity is still outstanding; once CE is completed, the same action succeeds.
  • Design note (FR-TP-5 scope): a dependency is a same-project prerequisite relationship (many-to-one is not enough — an activity can have several prerequisites, e.g. a report depending on every test activity that precedes it), stored as its own row per prerequisite rather than a single foreign key, and validated against both self-reference and circular chains when created. The block applies at the start/resume transition, mirroring FR-CON-2's scoping rationale (the same point precision already exists in the workflow); it deliberately does not block creating or scheduling a work order ahead of time.
  • Design note (FR-TP-7 scope): "the source template has since changed" is tracked as an integer version counter on the template (bumped on every item add/edit/delete/reorder), not a last-modified timestamp, since two changes landing in the same minute-resolution timestamp used elsewhere in this app would otherwise silently look simultaneous rather than out of order. Syncing a group only ever adds template activities missing from it (matched by name); it never removes or overwrites an activity already in the group, so a planner's own customizations to that activity are never silently lost.

8.3 Resources (FR-RES)

BR-003: Planning must reflect what can actually be booked — people, equipment, and labs alike — not just who is free.

  • FR-RES-1 [Must, Delivered - Phase 3]: The system shall store resources in these categories: test procedures, test equipment, test facilities/labs, test technicians, administrators, and test planners.
  • FR-RES-2 [Must, Delivered - Phase 3]: The system shall allow administrators full CRUD on user accounts, capabilities, and resources, and to assign/unassign capabilities on a resource.
  • FR-RES-3 [Must, Delivered - Phase 3]: The system shall allow planners to assign multiple resources to the same test activity (e.g. equipment, facility, procedure, and technician together), provided each has the activity's required capability, and to unassign any one independently.
  • FR-RES-4 [Must, Delivered - Phase 3]: The system shall prevent the same resource being assigned twice to the same test activity, and prevent deletion of a capability/resource/user still referenced elsewhere, reporting a clear reason.
  • FR-RES-5 [Should, Delivered - Phase 9]: A facility/equipment resource shall be able to record which site (TLC or TLS) it is at.
  • FR-RES-6 [Should, Delivered - Phase 20, extended Phase 21]: A resource's type shall be restricted to a fixed set (equipment, facility, technician, and - since Phase 21 - procedure), on both create and update, rather than accepted as free text - enforced server-side, not just as a UI picker.

8.4 Constraints (FR-CON)

BR-003 (continued): Some resources physically cannot serve two activities at once, and this must be enforced by the system rather than relied on from memory. This is the chapter the customer's consultant flagged as likely to become one of the most important.

  • FR-CON-1 [Must, Delivered - Phase 9]: The system shall let an administrator define mutual-exclusion groups of facility resources (e.g. "CON chamber: CE/CI" and "SAC chamber: RE/RI") such that two activities in the same group are treated as sharing one physical resource for conflict purposes.
  • FR-CON-2 [Must, Delivered - Phase 9]: The system shall block starting or resuming a work order if doing so would run it at the same time as another work order that is already in progress and shares a resource or exclusion group with it, and shall explain which work order/activity it conflicts with.
  • FR-CON-3 [Should, Delivered - Phase 15]: The Schedule view shall warn (not block) when the same shared equipment is used by two activities visible on the same day whose facilities put them at different sites, since moving equipment between sites also takes time not currently modeled.
  • FR-CON-4 [Could, Delivered - Phase 15]: The system shall let a facility reservation span multiple consecutive days as a single booking rather than one row per day, and shall warn when two such bookings on the same facility (or exclusion group) have overlapping planned windows.
  • Design note (FR-CON-3 scope): "overlapping windows" is already the existing hard-block/passive-conflict case (8.4), which treats same-equipment as an automatic collision regardless of site; FR-CON-3 is deliberately the complementary, non-overlapping case — the same equipment used at TLC then TLS (or vice versa) later the same day, with no explicit transit-time buffer modeled (see the matching open question in AI Questions). A pair already flagged as a hard conflict is not also flagged cross-site, to avoid two icons describing what is really one collision.
  • Design note (FR-CON-4 scope): a work order's actual start/complete timestamps, and (since Phase 14) an activity's planned start/end dates, are already each a single row spanning however many days they need — there was never a "one row per day" structure to eliminate. What was missing, and is now delivered, is a check that two planned (not yet started) bookings on the same facility/exclusion group don't silently overlap, since the existing conflict checks (8.4) only look at actual/inferred execution time, not the planner's forward-looking planned dates.
  • AC-FR-CON-2.1: Given RE's work order is in_progress in the SAC chamber, when a technician attempts to start or resume RI's work order (a different facility resource in the same "SAC Chamber (TLS)" exclusion group), then the system rejects the action and states which work order/activity it conflicts with.
  • Design note (scope of FR-CON-2): a work order's scheduled_date carries no time-of-day, so the block is applied at the point precision actually exists — the transition into "in progress" — rather than at creation-time scheduling, which would only support coarse same-day checks. The planner's Schedule/Gantt view (FR-PLN-3) additionally flags overlaps that arise after the fact (e.g. a test overrunning into the next one's actual start), as a passive check the hard block at start-time can't catch.

8.5 Calendar (FR-CAL)

BR-004: Scheduling decisions depend on who and what is actually available, which today lives in a separate hand-maintained block of rows at the top of Projects.xls.

  • FR-CAL-1 [Should, Delivered - Phase 12]: The system shall let an administrator record staff absence/vacation periods per technician.
  • FR-CAL-2 [Should, Delivered - Phase 12]: The system shall let a planner record customer on-site day(s) linked to a project.
  • FR-CAL-3 [Should, Delivered - Phase 12]: The schedule view shall visibly flag, for the day being viewed, any technician absence and any customer on-site visit that covers that date; the dashboard shall list upcoming absences (next 14 days) and each project's on-site visits.

8.6 Status Management (FR-STA)

BR-001 (continued): A test's status must be recorded once and reflected everywhere, closing the loop the customer described (testplan → Projects.xls → Sprint.xls, updated by hand up to four times per event).

  • FR-STA-1 [Must, Delivered - Phase 7]: The system shall move a work order through the lifecycle planned → in_progress → (on_hold/resumed) → completed, recording a pass/fail/n-a result and notes on completion.
  • FR-STA-2 [Should, Delivered - Phase 11]: A project's and a discipline's status (see Glossary) shall be derived from the status of their underlying test activities/work orders, not entered separately.
  • Design note (FR-STA-2 derivation and disciplines): a project's status is Completed once every activity's work order is completed; In Progress once any activity is (or has been) worked; Reporting once every non-Report activity is completed but at least one Report activity (test_name containing "report") isn't yet; otherwise Planned. A discipline groups activities via their required capability's admin-set discipline field (e.g. CE/CI/RE/RI → "EMC"); activities with no capability default to "Report" (by name) or "Project Management" (everything else, e.g. Kick-off/Testplan/EUT delivery/return) — a stopgap pending the customer confirming the real discipline taxonomy (see AI Questions).

8.7 Planning and Scheduling (FR-PLN)

BR-003 (continued): The core of "Projects.xls" is a day-by-day, resource-by-resource production schedule; RMS needs an equivalent that is generated, not hand-drawn.

  • FR-PLN-1 [Must, Delivered - Phase 3]: Every test activity shall be plannable by assigning it resources (equipment, facility, procedure, technician).
  • FR-PLN-2 [Should, Delivered - Phase 7 (WIP)]: The system shall provide a day-view production schedule showing each work order as a time-blocked bar against the resources/technician assigned to it, navigable by day.
  • FR-PLN-3 [Should, Delivered - Phase 9]: The schedule view shall display constraint conflicts (see 8.4) inline rather than requiring a separate check.
  • FR-PLN-4 [Should, Delivered - Phase 14]: See FR-TP-6 (planned start/end date on a test activity).
  • FR-PLN-5 [Should, Delivered - Phase 19]: In addition to the day-view chart (FR-PLN-2), the schedule shall offer a Week scale and a Month scale (1-day columns instead of 1-hour columns), each spanning a selectable number of weeks (default 1, up to 8) or months (default 1, up to 6), and an "All" mode showing Day, Week, and Month together (Day at top, Week below it, Month at the bottom). All three read the same work-order data as the Day chart and stay anchored to the same viewed date when switching between them.
  • Design note: the customer's spreadsheet plans in 2-hour blocks because that suits Excel's grid. RMS stores actual start/end timestamps internally (minute resolution) and only uses fixed blocks for the visual grid, so finer-grained scheduling is possible later without a data model change.
  • Design note (FR-PLN-5 scope): the Week/Month scales are visualization only - they reuse the Day chart's bar-placement logic at a coarser (1-day) granularity and deliberately do not re-run the Day chart's live conflict/cross-site overlay (FR-CON-2/3), which stays a Day-only feature, since checking every pair of activities across weeks or months of columns would be expensive and wasn't asked for; the underlying hard block at work-order start/resume (FR-CON-2) still applies regardless of which chart scale is being viewed.
  • FR-PLN-6 [Should, Delivered - Phase 28]: Unscheduled ordered tests (no work order yet) shall be shown as a queue, ordered so the earliest-needed test is first (by planned start date, then order/sequence), and shall be placeable onto a technician × day grid - by clicking a cell, by keyboard (Tab to a cell's placement control, Enter/Space to activate), or by dragging the queue card onto a cell. For each queued test the system shall propose a suggested placement (earliest technician holding the required capability who has no other non-completed work order and no staff absence that day, also checking any equipment/facility already allocated to the test for a same-day conflict), which the planner may accept in one step or override by placing on any other cell.
  • Design note (FR-PLN-6 scope): day-level only, matching the rest of the schema (no time-of-day column exists on work_orders/ordered_tests). Placing a test creates a work_order if none exists, or - while it is still status planned - updates one; once a work order is in_progress/on_hold/completed it can no longer be moved from this grid (a hard block, since by then real testing state exists). A technician/capability mismatch is a soft warning, not a hard block, deliberately consistent with the existing technician self-service work order creation (FR-PLN-1/Phase 7), which never enforced a capability match either - unlike FR-RES-3's hard-blocked resource↔capability match for equipment/facility/procedure assignment, where a wrong resource genuinely cannot do the job. Modern-only for the interactive grid/drag/keyboard (see docs/dual-ui.html section 8); Simple UI gets the same schedule_test action via a plain technician-select + date-input form per row, so no UI mode loses the ability to schedule a test.

8.8 Rescheduling (FR-RSC)

BR-005: When a test overruns, fails, is interrupted, or the customer sends replacement hardware, the remaining plan must be adjustable without manually touching many unrelated fields — the customer's consultant called this "the core of the system."

  • FR-RSC-1 [Must, Delivered - Phase 3/7]: Moving, reassigning, or changing the result of one test activity shall not require manually editing any other activity's stored data (each activity's schedule/resources/result are independent rows, not spreadsheet formulas referencing each other).
  • FR-RSC-2 [Could, Delivered - Phase 15]: When a prerequisite activity (per FR-TP-5) finishes late, or is still incomplete past its planned end date, the system shall suggest shifting its dependent activity's planned window by the same number of days, for the planner to accept (applying the shift) or ignore (dismissing the suggestion). Full automatic optimization/conflict auto-resolution is explicitly out of scope (Section 11) — this is assisted rescheduling, not automatic rescheduling.
  • Design note (FR-RSC-2 scope): "EUT replaced" is not implemented as a distinct trigger, since replacing an EUT isn't a distinct action anywhere in the system (only an EUT's own name/serial can be edited) — the delivered scope covers "delayed" (prerequisite still open past its planned end) and "late-finished" (prerequisite completed after its planned end), which are the cases with concrete data behind them. Once a suggestion is accepted or ignored, that specific prerequisite/dependent pair is not re-suggested (a small reschedule_dismissals table records this) — without it, an already-fixed historical delay would keep generating a fresh shift suggestion on top of the last one, since the prerequisite's lateness doesn't change after the fact.

8.9 Visualization and Dashboard (FR-VIS)

BR-004 (continued): The laboratory wants the at-a-glance overview Sprint.xls gives today, generated instead of hand-updated.

  • FR-VIS-1 [Should, Delivered - Phase 11]: The system shall provide a dashboard listing active projects with overall status, per-discipline status, and upcoming milestones, plus a read-only completed-project history view (FR-PRJ-4).
  • FR-VIS-2 [Should, Delivered - Phase 11]: The dashboard shall surface, per project: whether any of its currently in-progress activities has a live resource/exclusion-group conflict (8.4) with another project's activity, how many activities have no work order yet, and how many work orders are missing a test procedure.
  • FR-VIS-3 [Must, Delivered - Phase 7 (WIP)]: See FR-PLN-2 (production schedule chart).
  • FR-VIS-4 [Should, Delivered - Phase 14]: The dashboard shall flag, per project, whether any activity's planned end date (FR-TP-6) has passed without its work order being completed ("overdue"), as a derived flag alongside the existing conflict flag — not a replacement for the project's own computed status (FR-STA-2), since a project can be In Progress and overdue at the same time.

8.10 Reporting (FR-RPT)

BR-001 (continued): A test's pass/fail record and supporting checklist must be captured once, at the point of test, not transcribed later.

  • FR-RPT-1 [Must, Delivered - Phase 7]: The system shall let a test procedure be authored against a capability, with a summary, prose steps, required equipment/facility, safety notes, and an ordered checklist of check-items with pre-authored expected values.
  • FR-RPT-2 [Must, Delivered - Phase 7]: Once a work order has a procedure assigned, the system shall let its technician generate a test report pre-filled with test/order/equipment/technician identification and one fillable row per check-item.
  • FR-RPT-3 [Must, Delivered - Phase 7]: The system shall require every step and an overall result before a report can be submitted; submitting locks the report and time-stamps sign-off.
  • FR-RPT-4 [Must, Delivered - Phase 7]: The system shall let any technician other than the report's author, or a planner, approve or reject a submitted report (rejection requires a comment), and let the author reopen a rejected report.
  • FR-RPT-5 [Must, Delivered - Phase 7]: The system shall present the test report as a single printable A4 page, usable blank and completed, and provide a shared reports queue/history view.

8.11 Integrations (FR-INT)

No integration requirement was identified in customer discovery beyond replacing the three internal documents (Sprint.xls, Projects.xls, testplan) with RMS itself.

  • FR-INT-1 [Could, not scheduled]: Export a project's activities/results to a spreadsheet or PDF for customers/partners who are not RMS users, if a future need for this is confirmed.

8.12 Usability (FR-USE)

  • FR-USE-1 [Must, Delivered - Phase 3]: The system shall provide two interfaces over identical routes and data — "Simple" and "Modern" — switchable at any time, persisted for the session. See docs/dual-ui.html.
  • FR-USE-2 [Must, Delivered - Phase 7]: The technician workspace, work orders, procedure library, and test reports exist only in the Modern interface; a technician's session switches to Modern automatically on login.
  • FR-USE-3 [Must, Delivered - Phase 7]: The test report page shall render as a single A4 page with print-specific styling.
  • FR-USE-4 [Must, Delivered - Phase 8]: An anonymous visitor shall see a public landing page explaining RMS and prompting login, not the resource catalog or any other operational data; the resource catalog requires a signed-in admin, planner, or technician.
  • FR-USE-5 [Must, Delivered - Phase 8]: On login, and whenever a signed-in user visits /, the system shall route them directly to their own role's workspace (Admin, Planner, or Technician dashboard) rather than a shared landing/catalog page. The resource catalog remains implemented but is currently unlinked from navigation in every interface, pending a confirmed need for it.
  • FR-USE-6 [Should, Delivered - Phase 16]: The system shall provide a single-page, per-order workspace for creating and maintaining a customer order and everything directly attached to it — EUTs, test activities (with their dependencies, planned dates, and resource allocations), milestones, customer visits, and derived status — as an alternative to the multi-tab Planner page, so a planner working deeply on one order doesn't need to switch tabs to touch every part of it.
  • FR-USE-7 [Should, Delivered - Phase 20]: The Admin landing page shall keep its workflow explainer and its functional tab menu, but collapse its entity-count stat strip behind a small expand control by default; the workflow explainer's steps shall be clickable, jumping straight to the matching tab; and each tab label shall show its entity's total count beneath it, with a highlighted "(N!)" suffix when N of those entities need admin attention (e.g. an incomplete customer profile, a new proposal).

8.13 Feedback and Proposal Management (FR-FBK)

BR-008 [added Phase 22, retroactively covering the mechanism's use since shortly after Phase 3]: real usability gaps, bugs, and feature ideas surface while the customer and team actually use the running system, not up front - capturing them in a lightweight, in-app backlog tied to the exact page/screen in use, and letting the admin triage and track them through to done, is faster and more reliable than a separate ticket-tracking tool, and keeps this whole running project (see PROJECT_PLAN.md's Activity Log) grounded in real, dated, traceable requests rather than assumptions.

  • FR-FBK-1 [Should, Delivered - Phase 22 (mechanism itself pre-dates this requirement)]: Any signed-in user shall be able to open a lightweight "report an issue or idea" form from a floating button visible on every Modern-UI page (Simple UI: a dedicated page and nav link instead of a floating dialog, per its no-JS design), without losing their place on the page they're reporting against.
  • FR-FBK-2 [Should, Delivered - Phase 22, extended Phase 25]: A submitted proposal shall record: which type it is (Enhancement, Bug, or - since Phase 25 - New feature), a title, an optional description, who submitted it and when, which page and tab it was reported against (or flagged "General" if not tied to one specific view, since Phase 25), and its own numeric id for cross-referencing elsewhere (e.g. in this SRS's revision history and PROJECT_PLAN.md).
  • FR-FBK-3 [Should, Delivered - Phase 22, extended Phase 25/26]: An administrator shall be able to triage every proposal: edit its title, description, and type; move it through a status lifecycle (New → Accepted → In Progress → Done, with Rejected or Backlog available at any point, and a "Failed testing" status added Phase 26); leave an admin comment; and, once implemented, record a separate tester comment and test status (Waiting/Passed/Failed/Passed with comments, added Phase 26) as a lightweight verification step distinct from the admin's own status field.
  • FR-FBK-4 [Could, Delivered - Phase 25]: In the Modern interface, changing a proposal's Type, Status, or Test status shall save immediately, without a separate Save action and without triggering a spurious "leave without saving?" browser prompt (a real defect in the first implementation of this requirement, fixed the same phase it was found - see the Phase 26 entry in PROJECT_PLAN.md's Activity Log for the root cause).
  • FR-FBK-5 [Could, Delivered - Phase 22, extended Phase 26]: The Proposals tab label shall show the total number of proposals, with the count still New (needing initial triage) highlighted for attention, and the count Accepted-and-awaiting-implementation shown alongside it.
  • FR-FBK-6 [Could, Delivered - Phase 27]: In addition to the existing per-proposal Form view, an administrator shall be able to switch to a Table view of the same proposals in the Modern interface: a keyboard-navigable editable grid (arrow keys/Tab/Enter to move the active cell; click, shift-click, a row handle, a column header, or the top-left corner cell to select a cell range/row/column/everything; Ctrl+C/Ctrl+X/Ctrl+V; Ctrl+Z undo; a per-column wildcard/OR filter row; and a "select 2+ rows, edit the first, Ctrl+R to repeat" bulk-edit tool), exposing every field FR-FBK-2/3 define except the proposal's own identity and audit trail (id is shown but read-only; description, reported-against page, submitter, and submission time remain Form-view only). Saving from Table view updates existing proposals by id only - it cannot create a new proposal (submit one via FR-FBK-1 instead) or delete one (use the Form view's Delete button).
  • Design note (FR-FBK-6 implementation): the editable grid is one reusable client-side component (RmsSandbox.createEditableGrid() in app/static/js/sandbox.js) shared with an admin-only internal prototyping area (/sandbox/*, not linked from any real navigation and not itself part of this requirement) where the interaction pattern was first trialled and refined before being pointed at real proposal data. See docs/design-guide.html section 6 and docs/architecture.html for implementation detail.
  • Design note (FR-FBK scope): this whole area intentionally has no Must-priority requirement and no dedicated data-integrity constraints beyond basic type/status validation - it is an internal working tool for this project's own development process, not a customer-facing capability of the resource-management domain (Sections 8.1-8.11), which is why it sits last among the functional areas despite having accumulated the most individual delivered increments of any single area in this document.

8.14 Nice-to-have (FR-NTH)

  • FR-NTH-1 [Could, Delivered - Phase 13]: The system shall keep a change history per test activity ("who moved this test, when, and — where provided — why"), viewable alongside the activity.
  • Design note (FR-NTH-1 scope): history is recorded automatically for schedule-affecting changes — resource assignment/removal, reordering, EUT reassignment, and the work order lifecycle (created/started/held/resumed/completed, procedure changed) — rather than requiring every action to prompt for a reason. "Why" is only ever populated when the acting workflow already collects a note (currently: the technician's completion notes); every other entry's "why" column is blank, which is expected, not missing data.
  • FR-NTH-2 [Could, not scheduled]: Alternate/what-if scheduling (propose an alternative plan without committing it).
  • FR-NTH-3 [Could, not scheduled]: File/photo attachments on test reports.

9. Data Requirements

  • Store users, roles (including a technician's optional link to their own resource), resources, and capabilities with many-to-many mapping.
  • Store projects (customer_orders), and — from Phase 8 — EUTs per project, and an optional EUT reference on each test activity.
  • Store test activities (ordered_tests) and resource allocations.
  • Store test procedures and their ordered check-items (description + expected value).
  • Store work orders (one per test activity) with lifecycle status, schedule/execution timestamps, and result.
  • Store test reports (one per work order) with unit-under-test identification, snapshotted report steps, overall result, notes, and technician/reviewer sign-off fields.
  • From Phase 9 (delivered): mutual-exclusion groups and their facility-resource membership, and a site field on resources.
  • From Phase 10 (delivered): activity templates and their ordered items (activity name + optional required capability), and an optional sequence number on each test activity, scoped per order/EUT, so activities can be freely reordered.
  • From Phase 11 (delivered): an optional discipline field on capabilities; a weekly note and a waiting-for-customer flag on each project (the only two manually-entered project-status fields); milestones per project (title, optional target date, optional notes).
  • From Phase 12 (delivered): staff absences per technician resource (start/end date, optional reason), admin-managed; customer on-site visits per project (start/end date, optional notes), planner-managed.
  • From Phase 13 (delivered): an append-only change history per test activity (when, who, a system-generated description of what changed, and an optional why), covering resource assignment/removal, reordering, EUT reassignment, and the work order lifecycle.
  • From Phase 14 (delivered): an optional planned start date and planned end date on each test activity; a same-project activity-dependency record (one row per prerequisite, so an activity can have more than one), validated against self-reference and circular chains at creation time.
  • From Phase 15 (delivered): a dismissal record per (dependent activity, prerequisite) pair, so an ignored or already-applied reschedule suggestion is not repeated. No other new stored data — the cross-site and planned-overlap warnings are computed at read time from data Phase 9/14 already store (a resource's site, and an activity's planned dates).
  • Phase 16 added no new stored data at all — the order workspace page is a new arrangement of the same order/EUT/activity/milestone/visit/status data the tabbed Planner page and Dashboard already read and write, through the exact same actions.
  • From Phase 17 (delivered): a customers table (name, optional contact name/email/phone/address, created-by/at); an optional customer_id on customer_orders linking to it, alongside the existing customer_name (kept as a denormalized snapshot so every existing display/report is unaffected).
  • From Phase 18 (delivered): a template_applications table (one row per "apply template" action: which template, order, optional EUT, when, and whether any member has since been individually changed) and an optional template_application_id on ordered_tests linking an activity back to the batch that created it; an integer version counter on activity_templates for drift detection.
  • Phase 19 added no new stored data at all — the Week/Month schedule scales read the same work_orders/ordered_tests records the Day chart already reads, just windowed and placed at a coarser (1-day) granularity.
  • From Phase 12: staff absence periods and customer on-site day records.
  • From Phase 13: an append-only history/audit record for schedule-affecting changes.
  • A proposals table (see FR-FBK, 8.13), added not long after Phase 3 and extended in place several times since without ever renaming or removing a column: id, reported-against path, type (enhancement/bug/new_feature), title, optional description, submitter/timestamp, status (new/accepted/in_progress/done/rejected/backlog/failed_testing), optional admin comment, an is_general flag (Phase 25), and an optional tester_comment plus a test_status (waiting/passed/failed/passed_with_comments, Phase 26). Widening the type/status CHECK constraints each time required a full table rebuild-and-rename rather than a plain column add, since SQLite cannot alter a CHECK already attached to a column - the same technique already used for the users table.
  • Phase 27 added no new stored data — the Proposals Table view (FR-FBK-6) reads and updates the same proposals rows the Form view already does, just through a different UI.
  • Not part of the resource-management domain: a throwaway sandbox_items table (Phase 22) backing the admin-only editable-grid prototyping area (/sandbox/*) referenced in FR-FBK-6's design note - no foreign keys, no CHECK constraints, freely resettable, and not a business entity.

11. Out of Scope

  • Advanced scheduling optimization and fully automatic conflict auto-resolution (FR-RSC-2 is assisted suggestion only, not automation).
  • Production-grade identity management (passwords, SSO, MFA).
  • Digital/cryptographic signatures for report sign-off (a simple username + timestamp record, not a legally-binding e-signature).
  • Multi-level or multi-reviewer approval chains beyond a single reviewer decision.
  • File/photo attachments on test reports (FR-NTH-3).
  • External system integrations (FR-INT-1) unless a concrete need is confirmed.

13. Assumptions and Open Questions

  • Assumed: a test activity's optional EUT reference does not become mandatory in Phase 8, so existing single-EUT projects keep working without data migration of existing rows. Revisit once multi-EUT usage is confirmed as the common case. See also AI Questions and Priorities for the running list of business-rule questions (conflict handling detail, capacity limits, priority rules) raised during Phase 1 and still open.
  • Open: should the project (not the EUT) remain the primary planning unit for very small single-EUT orders? See Section 2's design note.
  • Open: is a spreadsheet/PDF export (FR-INT-1) actually needed, or does customer-facing reporting stay inside RMS?
  • Assumed (Phase 9): the confirmed exclusion-group examples are "CON chamber: CE/CI" and "SAC chamber: RE/RI"; is this the complete list, or are there other shared facilities/equipment we haven't heard about yet?
  • Open: should FR-CON-2's block also apply at creation-time scheduling (same-day, coarse) rather than only at the in-progress transition, once the team has an opinion on how often two conflicting activities get scheduled for the same day without anyone noticing before start time?
  • Assumed (Phase 10): one template ("Standard EMC Test Sequence") covers the customer's example workflow; is more than one standard sequence needed in practice (e.g. per product category or per site), and if so should a template itself record which EUT/product types it's meant for?
  • Assumed (Phase 11): the discipline groupings seeded so far (Calibration, Environmental, EMC) and the two name-based fallback buckets (Report, Project Management) are a stopgap, not the confirmed taxonomy — see the matching open question in AI Questions.
  • Open (Phase 11): is "Waiting for Customer" the only manually-flagged project state needed, or are there other externally-caused holds (e.g. "waiting on a spare part", "lab closed") that deserve their own flag rather than being folded into the free-text weekly note?
  • Open (Phase 12): the schedule's absence/visit banner only checks the single day being viewed; a multi-day absence/visit is otherwise invisible until you navigate to a day inside it. Is a compact "this week at a glance" strip worth adding, or is per-day plus the dashboard's 14-day absence list enough?
  • Open (Phase 13): should test activity edits (name/required capability changes, not just EUT/sequence) also be logged, or is the current schedule-affecting-only scope the right line? Should a project-level history view (across all its activities at once) be added, or is per-activity enough?
  • Assumed (Phase 14): a dependency is scoped to within one project (order), not across projects — no customer example so far crosses that boundary. Revisit if a real cross-project dependency need surfaces.
  • Open (Phase 14): the dependency block only fires at the work-order start/resume transition (mirroring FR-CON-2); is a same-day, creation-time warning also wanted, the way it was raised for FR-CON-2 above?
  • Open (Phase 14): should an activity template (FR-TP-4) be able to pre-declare its own standard dependencies (e.g. "Report writing" template item always depends on every non-Report item before it), so applying a template also wires up dependencies automatically instead of the planner adding them by hand each time?
  • Partially answered (Phase 15): the cross-site warning (FR-CON-3) uses same-calendar-day as its transit-time proxy (any two activities visible on the same Schedule day, sharing equipment, at different sites) rather than a specific minimum transit/setup duration, since that number is still unconfirmed (see the existing Phase 9 open question above) — if a real transit time is confirmed later, the same-day check could be tightened to a precise buffer window instead.
  • Open (Phase 15): reschedule suggestions (FR-RSC-2) only trigger from a completed prerequisite that finished late, or an incomplete one already overdue - is a suggestion also wanted the moment a prerequisite's work order is marked on_hold or failed, ahead of its planned end date passing?
  • Open (Phase 15): once a reschedule suggestion is accepted or ignored, that exact (dependent, prerequisite) pair is never re-suggested, even if the prerequisite's delay later changes (e.g. it's fixed after being on hold, or a different prerequisite also becomes late). Is a way to reset/re-trigger a dismissed suggestion needed, or is manually editing the planned dates enough?
  • Open (Phase 16): the order workspace deliberately excludes the day-view Schedule/Gantt tab (it's cross-order by nature - it shows a whole day across every order, not one order's own timeline) and links out to the tabbed Planner page for it instead. Is a per-order timeline strip (just this order's activities, across whichever days they touch) worth adding to the workspace directly?
  • Open (Phase 16): should the tabbed Planner page's five tabs eventually be retired in favor of the workspace plus a portfolio-level list/board (the existing Orders Overview tab already covers that), or do both belong side by side long-term for different working styles?
  • Open (Phase 27): now that Option C's editable-grid pattern has been integrated into a real feature (FR-FBK-6), is the standalone admin-only sandbox area (/sandbox/* - Option A, Option B, and Option C's own page) still worth keeping as a live route, or should it be retired/archived now that its job (deciding which prototype to build for real) is done? Nothing currently links to it from any real navigation, so leaving it in place costs little, but it is one more area a new team would need to be told is not a product feature.
  • Open (Phase 27): FR-FBK-6's Table view is deliberately update-only (no add/delete-row), since proposals carry audit fields (id, created_at, submitted_by_username) the grid never exposes. If a future need arises to delete several proposals at once from Table view (rather than one at a time via the Form view's Delete button), should that be added as a scoped exception, or does the existing per-row Delete stay the only deletion path by design?
  • Open (Phase 22-27, FR-FBK generally): this whole area has grown organically, one proposal at a time, into a real internal tool with its own type/status/test-status vocabulary and two full UI views. Is it worth eventually exposing to the customer as a supported "feature request" channel (a real product capability, raising it out of Section 8.13's self-acknowledged internal-tooling framing), or should it stay strictly an internal development-process tool, not part of what's delivered to the customer?
  • Open (Phase 28): FR-PLN-6 is deliberately day-level only, matching the rest of the schema. Is time-of-day scheduling (a real schema change - new columns or a slot table) worth the migration once day-level usage of the Visual Schedule tab is proven out, or does day granularity stay sufficient given the lab's actual throughput?
  • Open (Phase 28): the Visual Schedule grid only accepts drops/placements from the unscheduled queue; an already-placed test's chip on the grid is not itself draggable to a different technician/day (rescheduling a placed-but-not-started test still requires re-submitting through the same queue-based flow, which only works while it's still unscheduled - once placed, only the technician's own workspace or a direct DB edit can move it). Is drag-to-reschedule an already-placed chip worth adding as a Phase 2, now that the placement endpoint (schedule_test) already supports updating a still-planned work order?
  • Open (Phase 28): suggest_placement's resource-availability check only looks at equipment/facility already allocated to the specific test being placed (a day-granularity same-resource conflict), not the exclusion-group logic the Day chart's live conflict overlay uses (FR-CON-2/3) or a look-ahead that tries alternate technicians/days more exhaustively when the first available slot's other resources turn out to conflict. Is it worth folding exclusion-group awareness into the suggestion algorithm, or does the existing hard block at work-order start (FR-CON-2) remain sufficient as the real safety net regardless of what the suggestion recommended?
