Resource Management System (RMS) - SRS v2

Version: 0.2 | Date: 2026-07-28

Back to Documentation Home

1. Purpose

This SRS defines the requirements for the working demonstrator of a web-based RMS for a small test company, from resource/capability setup and order allocation (v1) through technician execution and test reporting (v2, this revision).

2. Business Context

  • The company performs electrical and mechanical tests on customer products.
  • The RMS supports planning and allocation of resources to customer orders, and the technician's execution of and reporting on the tests themselves.
  • Example orders include multimeter calibration and vibration/humidity tests for a mobile phone under development.

3. User Roles (v2)

  • RMS Administrator: manages resources, capabilities, assignments of capabilities to resources, user accounts, and a technician user's link to their own technician resource.
  • Test Planner: assigns resources to customer orders.
  • Test Technician: works the tests assigned to them — runs a work order against a documented test procedure, fills in and submits the resulting test report, and reviews/approves or rejects reports submitted by other technicians.

4. Core Functional Requirements

4.1 Resource and Capability Management

  • The system shall store resources in these categories: test procedures, test equipment, test facilities, test technicians, administrators, and test planners.
  • The system shall allow administrators full CRUD (create, read, update, delete) on user accounts, capabilities, and resources.
  • The system shall allow administrators to assign and unassign capabilities on a resource.
  • The system shall allow administrators to link a technician's user account to the technician resource that represents them, which determines which allocated tests appear on that user's technician workspace.
  • The system shall prevent deletion of a capability, resource, or user that is still referenced by an ordered test, allocation, or planner assignment, and shall report a clear reason instead of failing silently.

4.2 Customer Orders and Allocation

  • The system shall allow planners full CRUD (create, read, update, delete) on customer orders and ordered tests.
  • The system shall allow planners to assign multiple resources to the same ordered test (e.g. equipment, facility, procedure, and technician together), and to unassign any one of them independently, provided each assigned resource has the test's required capability.
  • The system shall prevent the same resource from being assigned twice to the same ordered test.
  • Deleting a customer order shall also remove its ordered tests and all of their allocations; deleting an ordered test shall also remove all of its allocations, work order, and test report.

4.3 Test Procedure Library

  • The system shall let a test procedure be authored against a capability, with a summary, prose process steps, required equipment/facility, and safety notes.
  • The system shall let a test procedure carry an ordered checklist of check-items, each with a pre-authored expected value (acceptance criterion), for use when generating a test report.
  • The system shall present the procedure library to technicians as read-only reference material.

4.4 Work Orders

  • The system shall show each technician the ordered tests where their linked resource has been allocated by a planner, together with the other resources (equipment/facility) allocated to that same test.
  • The system shall let a technician create at most one work order per assigned ordered test, optionally selecting a test procedure at creation or afterward.
  • The system shall move a work order through the lifecycle planned → in_progress → (on_hold/resumed) → completed, recording a pass/fail/n-a result and notes when completed.

4.5 Test Reports and Review/Approval

  • Once a work order has a test procedure assigned, the system shall let its technician generate a test report template pre-filled with: the test name; the order/customer/product; the equipment and facilities allocated to the test; the technician's name; the unit-under-test's name (defaulted from the order's product) and an editable serial number field; and one fillable row per procedure check-item, each showing its expected value with blank actual-value and pass/fail/n-a fields.
  • The system shall let the authoring technician fill in the unit-under-test details, each step's actual value and result, an overall result, and notes, and save the report as a draft any number of times before submitting.
  • The system shall require every step to have a result and an overall result to be set before a report can be submitted; submitting shall lock the report to further edits by its author and time-stamp the technician's sign-off.
  • The system shall let any technician other than the report's author, or a planner, approve or reject a submitted report; rejecting shall require a comment explaining what needs to change.
  • The system shall let the authoring technician reopen a rejected report for correction and resubmission.
  • The system shall present the test report as a single printable A4-format page, usable both as a blank fill-in form during the test and as the final signed record afterward.
  • The system shall provide a shared reports view listing reports awaiting the current user's review and the full report history, for technicians and planners.

4.6 Access Control (Basic)

  • The system shall enforce basic role checks for admin-only, planner-only, and technician-only actions, and shared technician-or-planner access to the test reports view.
  • The system shall enforce, in application logic, that a test report can only be edited/submitted by its own technician, and can only be reviewed by someone other than its own technician.

5. Data Requirements

  • Store users, roles (including a technician's optional link to their own resource), resources, and capabilities with many-to-many mapping.
  • Store customer orders, ordered tests, and resource allocations.
  • Store test procedures and their ordered check-items (description + expected value).
  • Store work orders (one per ordered test) with lifecycle status, schedule/execution timestamps, and result.
  • Store test reports (one per work order) with unit-under-test identification, snapshotted report steps (description, expected value, actual value, result), overall result, notes, and technician/reviewer sign-off fields.

6. Non-Functional Requirements

  • Technology: Python with Flask.
  • Local first: working local version uses SQLite.
  • Cloud target: Railway hosting in later stage.
  • Documentation: SRS, architecture, ER model, development plan, and AI questions page in HTML.
  • Usability: the system shall provide two interfaces over identical routes and data — "Simple" (plain, dependency-free) and "Modern" (styled, tabbed, usability-focused, with help pages) — switchable at any time via a button present in both, with the choice persisted for the session. See docs/dual-ui.html.
  • Usability (v2 addition): the technician workspace, work orders, test procedure library, and test reports exist only in the Modern interface, since this workflow has no Simple-interface counterpart; a technician's session is switched to Modern automatically on login.
  • Printability: the test report page shall render as a single A4 page with print-specific styling that removes site navigation/chrome, suitable for printing or saving as PDF both before and after test completion.

7. Out of Scope

  • Advanced scheduling optimization and conflict auto-resolution.
  • Production-grade identity management (passwords, SSO, MFA).
  • Digital/cryptographic signatures for report sign-off (v2 uses a simple username + timestamp record, not a legally-binding e-signature).
  • Multi-level or multi-reviewer approval chains beyond a single reviewer decision.
  • File/photo attachments on test reports.
